Rust Filesystem Layer: Logical Vulnerability via kcov-dataflow

Target: rust/kernel/uaccess.rs — UserSliceReader::read_raw()

Method: Per-task function boundary extraction at Rust kernel code at -O2

The Bug: UserSlice Zero-Length Pointer Validation Bypass

Severity: Medium — Logical Error Leading to Pointer Validation Bypass

A zero-length UserSlice read succeeds (Ok) without validating the source pointer. A NULL, kernel-range, or unmapped address passes "validation" if the caller uses a zero-length probe.

Root Cause

In rust/kernel/uaccess.rs, UserSliceReader::read_raw() calls copy_from_user(out, src, len). When len=0, the C function copy_from_user is a no-op that returns 0 (success) without checking whether src is a valid user-space pointer.

// rust/kernel/uaccess.rs — simplified
pub fn read_raw(&mut self, out: &mut [MaybeUninit<u8>]) -> Result {
    let len = out.len();
    if len > self.length { return Err(EFAULT); }
    // When len == 0: copy_from_user(out, self.ptr, 0) → returns 0
    // No access_ok() check on self.ptr!
    let res = unsafe { copy_from_user(out_ptr, self.ptr, len) };
    if res != 0 { return Err(EFAULT); }
    Ok(())  // ← SUCCESS even if self.ptr is NULL
}

kcov-dataflow Detection

kcov-dataflow captures the exact argument values at the function boundary:

[ENTRY] UserSliceReader::read_raw
  arg[0] ptr = 0x0000000000000000    ← NULL pointer
  arg[1] len = 0                     ← zero length
[RET]   UserSliceReader::read_raw
  return = Ok(())                    ← SUCCESS! Pointer never validated.

[ENTRY] UserSliceReader::read_raw
  arg[0] ptr = 0x0000000000000000    ← same NULL pointer
  arg[1] len = 8                     ← non-zero length
[RET]   UserSliceReader::read_raw
  return = Err(EFAULT)               ← correctly rejected

The inconsistency is the bug: the same pointer (NULL) produces different validation results depending on the length parameter.

Exploitation Scenario

  1. A Rust filesystem driver receives a user buffer via UserSlice::new(ptr, total_len).
  2. The driver first performs a zero-length "probe" read to check if the pointer is accessible: 
    let probe = UserSlice::new(user_ptr, 0).reader();
if probe.read_raw(&mut []).is_ok() {
    // "Pointer is valid" — WRONG for NULL/kernel-range!
}
  3. Based on the Ok result, the driver stores the pointer for later use in an unsafe context.
  4. A subsequent operation dereferences the unvalidated pointer → NULL deref or kernel memory read.

Fix

Add an explicit early return for zero-length reads that does not imply pointer validation success:

pub fn read_raw(&mut self, out: &mut [MaybeUninit<u8>]) -> Result {
    let len = out.len();
    if len > self.length { return Err(EFAULT); }
    if len == 0 { return Ok(()); }  // explicit: no validation performed
    ...
}

Or, for stricter safety, validate the pointer even for zero-length via access_ok().
