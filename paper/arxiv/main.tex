\begin{abstract}
Coverage-guided kernel fuzzers such as syzkaller rely on edge coverage
(\texttt{trace-pc}) as their sole feedback signal. This context-blind approach
cannot distinguish execution paths that differ only in argument values---for
example, two invocations of \texttt{copy\_from\_user()} with different size
parameters hit identical basic blocks yet have vastly different security
implications. I present \toolname{}, an LLVM-based instrumentation framework
that extends Linux KCOV with data-flow extraction of function arguments and
return values. A compiler pass emits lightweight callbacks that report one
source-level parameter per call, passing the value itself in a register
together with its index and byte size. A composite is instead reported by the
address of the object holding it, paired with a constant table of field
(offset, size) pairs derived from DWARF \texttt{DICompositeType} metadata, with
zero source annotation. The callbacks carry no program counter---the kernel
derives it from the return address, which also attributes records the compiler
emitted from inside an inlined body to the callee that was inlined. A lock-free
per-task record buffer delivers variable-length records to user space with no
interference to existing KCOV or syzkaller infrastructure, carrying entry,
return, and comparison-operand records in one unified stream. I demonstrate dual utility:
(1)~fuzzers gain state-aware feedback for mutation guidance into
value-dependent state transitions, and (2)~security analysts obtain
deterministic argument records for root-cause analysis without
\texttt{printk} or kprobe overhead. Two Rust instrumentation paths are
provided: a post-compilation pipeline requiring no rustc modification, and
native instrumentation via rustc built against the custom LLVM. Both decode
idiomatic Rust arguments, which \texttt{ftrace} cannot---it can place a probe,
since rustc does emit \texttt{\_\_fentry\_\_} stubs, but its BTF-based argument
printing expects \texttt{repr(C)} shapes Rust types need not have, and is
capped at six parameters---and which \texttt{drgn}/vmcore cannot either, as
\texttt{-O2} elides the DWARF variable locations it reads.
\end{abstract}

\section{Introduction}\label{sec:intro}

The Linux kernel exceeds 44 million lines of tracked source (38.4M of it C,
headers, and assembly), integrates Rust ($\sim$199k lines, 160k of them in
\texttt{rust/}) as a second
systems language, and implements complex locking hierarchies
(\texttt{rwsem}, \texttt{mutex}, RCU) that create deep state spaces unreachable
by coverage-guided fuzzing alone. syzkaller~\cite{vyukov2015syzkaller} has
discovered over 5{,}000 kernel bugs in the linux kernel, yet plateaus on stateful
subsystems such as \texttt{ksmbd}, \texttt{io\_uring}, and \texttt{binder}
where security-critical behavior depends on runtime argument values rather than
control-flow topology.

The fundamental limitation is a \emph{semantic gap}: KCOV's \tracepc reports
\emph{which} basic blocks executed but not \emph{with what values}
(Figure~\ref{fig:blind-spot}). Two
executions of \texttt{vfs\_open()} with different access-mode flags traverse
identical edges yet have entirely different security implications. Fuzzers
cannot distinguish these without data-flow context, leading to coverage
saturation on value-dependent state transitions.

Prior approaches each fall short for kernel-scale deployment. Dynamic tracing
via \texttt{ftrace}/\texttt{kprobes} imposes per-function overhead unsuitable
for continuous fuzzing. IJON~\cite{aschermann2020ijon} requires manual
annotation---infeasible for 30M~LOC. Context-sensitive coverage
(Angora~\cite{chen2018angora}, CollAFL~\cite{gan2018collafl}) clones call sites
but explodes on polymorphic dispatch (\texttt{file\_operations} alone has 20+
function pointers). DataFlowSanitizer provides byte-level taint tracking but
imposes 10--100$\times$ overhead, rendering it unusable for kernel fuzzing.

I observe that \emph{function boundaries} are natural chokepoints where
data-flow context is both cheap to capture and highly informative. Arguments
encode the \emph{intent} of a call; return values encode the \emph{outcome}.
Capturing these at compile time with a lock-free kernel transport gives both
fuzzers and analysts a new dimension of observability without source annotation.

\toolname{} is an automated LLVM IR instrumentation framework that reports every
function boundary with a five-operand callback
$\langle \mathit{arg\_idx}, \mathit{size}, \mathit{val},
\mathit{offsets}, \mathit{num\_fields} \rangle$,
which the kernel turns into a record
$\langle \mathit{PC}, \mathit{arg\_idx}, \mathit{size},
\mathit{address}, \mathit{values}[\,] \rangle$.
It operates through three layers:
\begin{enumerate}[nosep]
  \item A compiler pass that emits callbacks reporting a register-resident
        value directly, and a composite by address plus a DWARF-derived field
        table.
  \item A kernel-resident lock-free per-task record buffer delivered through a
        separate \texttt{/sys/kernel/debug/kcov\_dataflow} dedicated debugfs interface.
  \item A user-space consumer interface for both fuzzer executors and human
        analysts.
\end{enumerate}

My contributions are:
\begin{itemize}[nosep]
  \item An LLVM \sancov extension\footnote{\url{https://github.com/llvm/llvm-project/pull/201410}} that reports function arguments and return
        values as \emph{source-level} parameters---one call per declared
        parameter, including the parameters of callees the inliner merged
        away---with automatic struct field expansion via
        \texttt{DICompositeType} metadata and zero source annotation.
  \item A lock-free, per-task kernel transport mechanism that operates safely in
        sleepable task context, rejecting interrupt and nofault contexts, and
        collecting from kernel threads through a remote-handle path, without
        interfering with existing KCOV or syzkaller infrastructure.
  \item A post-compilation pipeline enabling Rust kernel module instrumentation
        without modifying the Rust compiler toolchain, and a native path via
        rustc built against the custom LLVM.
  \item A self-checking in-tree selftest suite---four kernel modules (two C,
        two Rust) and two user-space tests---that pins down what the
        instrumentation reports and, equally, where it stops: the eight-deep
        value-nested and pointer-linked struct towers assert the shallow-capture
        boundary rather than leaving it as an assumption.
\end{itemize}


\section{Background \& Motivation}\label{sec:background}

\subsection{KCOV and Coverage-Guided Kernel Fuzzing}

KCOV~\cite{vyukov2016kcov} instruments the kernel at compile time via
\sancov's \tracepc callback. Each task owns a kernel-allocated buffer,
memory-mapped into user space, into which the kernel writes the program
counter of every executed edge. User-space fuzzers (primarily syzkaller)
hash these PCs into a coverage signal, retaining inputs that discover
novel edges in the corpus.

This architecture has proven remarkably effective: syzkaller continuously
discovers 100+ bugs per month across upstream kernels. However, coverage
\emph{saturates} on stateful subsystems. After initial exploration, new edges
become rare, and the fuzzer degenerates into random mutation without meaningful
guidance.

Consider the \texttt{ksmbd} SMB2\_CREATE handler. Before a file operation
reaches the VFS layer, ksmbd enforces a multi-stage protocol handshake
between the client (fuzzer) and the in-kernel SMB server
(Figure~\ref{fig:ksmbd}). A fuzzer must produce valid negotiate, authenticate,
and tree-connect messages before it can exercise the file-create path. Once
coverage of this multi-stage sequence saturates, all subsequent CREATE requests
traverse identical edges regardless of \texttt{DesiredAccess}---the fuzzer
cannot distinguish \texttt{FILE\_READ\_DATA} from
\texttt{FILE\_WRITE\_DATA|FILE\_DELETE\_ON\_CLOSE}. With \toolname{}, the
\texttt{DesiredAccess} value becomes visible---though not, as it happens, at
the \texttt{smb2\_open()} boundary. That function takes a single
\texttt{struct ksmbd\_work *}, and the request lives two levels down, behind
that struct's \texttt{void *request\_buf}: an opaque pointer, whose pointee
layout the compiler cannot describe, followed by the request struct itself.
One level of dereference reaches \texttt{request\_buf}'s \emph{value} and stops
(Section~\ref{sec:deref}). The field is instead captured where a callee
receives it as a value---\texttt{smb\_map\_generic\_desired\_access(\_\_le32
daccess)}, and \texttt{smb\_check\_perm\_dacl()}, which takes
\texttt{req->DesiredAccess} as its fourth argument. Both are on the CREATE
path, so the value is recorded on every request; it is simply recorded one
frame deeper than the handler. This is the motivating example and also the
clearest case of why the one-level rule matters in practice.

Reaching those boundaries requires the remote path rather than plain per-task
collection: ksmbd processes requests on kernel work queues, not in the syscall
context of the client, so \texttt{fs/smb/server/} annotates its connection
handler and request dispatcher with
\texttt{kcov\_df\_remote\_start\_common()} /
\texttt{kcov\_df\_remote\_stop()} (Section~\ref{sec:device}). That is the
reason the transport cannot be per-task only.

A second example arises at Rust-to-C FFI boundaries. A Rust wrapper calls a C
function with a struct pointer whose fields determine kernel behavior. Edge
coverage sees one call site; the struct contents---which control whether a
privilege check is bypassed---are invisible.

\subsection{Threat Model and Assumptions}

I assume a standard kernel fuzzing threat model: an unprivileged user-space
process with access to the syscall interface attempts to trigger memory
corruption in kernel subsystems. KASAN/KMSAN detect the corruption once
triggered; my tool provides the \emph{path to triggering} it and the
\emph{data for triaging} it. Debug information is not optional on the kernel
side: \texttt{CONFIG\_KCOV\_DATAFLOW\_ARGS} and \texttt{\_RET} both
\texttt{depend on DEBUG\_INFO}, so any kernel that can enable the feature can
expand struct fields. The graceful degradation to register-value-only capture
applies to the compiler pass in general---a translation unit built without
\texttt{-g} still reports scalars---not to a kernel configuration. The Kconfig
options additionally depend on \texttt{CC\_IS\_CLANG} and on
\texttt{cc-option}/\texttt{rustc-option} probes for the two flags, so they do
not appear at all on a toolchain lacking the pass.


\section{System Design \& Architecture}\label{sec:design}

\subsection{Overview}

\toolname{} operates as a three-layer pipeline: (1)~compile-time
instrumentation inserts data-flow callbacks into kernel object files,
(2)~a runtime transport layer delivers records to user-space via a lock-free
per-task record buffer, and (3)~user-space consumers (fuzzer executors or analyst
tools) read the buffer via \texttt{mmap()} (Figure~\ref{fig:arch}). The system is activated by the
compiler flags \texttt{-fsanitize-coverage=trace-args,trace-ret} and
requires no source-level annotation.

\subsection{LLVM IR Boundary Instrumentation}\label{sec:llvm-pass}

The instrumentation pass resides in LLVM's existing \sancov framework
(\texttt{SanitizerCoverage.cpp}). It reports \emph{source-level} parameters, not
IR arguments: for each function~$F$ carrying a \texttt{DISubprogram}, the pass
recovers the declared parameter list from debug info and reports one callback
per declared parameter.

\paragraph{Argument Capture.} At each frame's first legal insertion point, for
each declared parameter~$i$:
\begin{enumerate}[nosep]
  \item Resolve the parameter's \texttt{DILocalVariable} to the IR value (or
        values, when a \texttt{DW\_OP\_LLVM\_fragment} split it across
        registers) that holds it, and to its \texttt{DIType}.
  \item If that type is a pointer to a \texttt{DICompositeType}, or the
        composite itself, walk the composite's \texttt{DW\_TAG\_member} list
        and emit a private constant global
        \texttt{[off$_0$, sz$_0$, off$_1$, sz$_1$, \ldots]}---a flat array of
        $2N$ 64-bit words, one \emph{(offset, size)} pair per field, in bytes.
        A bitfield is widened to the bytes that hold it rather than reported as
        zero-sized. Tables are cached per \texttt{DICompositeType}, so one
        global is shared by every parameter of that type in the module.
  \item Insert a call to
        \texttt{\_\_sanitizer\_cov\_trace\_args(arg\_idx, size, val,
        offsets, num\_fields)} (Figure~\ref{fig:abi}).
\end{enumerate}

\paragraph{Values remain values.} The callback's \texttt{val} operand is an
\texttt{i64} passed \emph{in a register}. A value that fits in one---an
integer, a pointer, a floating-point value---is widened in place
(\texttt{zext}, \texttt{ptrtoint}, or \texttt{bitcast} of the bit pattern) and
reported as it comes, with \texttt{offsets} null and \texttt{num\_fields}
zero. No \texttt{alloca} is introduced and no memory is touched, so the pass
does not force a value onto the stack that the ABI kept in a register. Only a
composite whose fields are described is reported indirectly, and then
\texttt{val} is the \emph{address} of the object and \texttt{size} is the
object's size in bytes. A parameter the compiler cannot report at all is sent
with \texttt{size}~0, which the kernel records as an explicit
``no value'' marker rather than silently omitting the parameter.

\paragraph{Inlined frames.} Because the pass keys on debug info rather than on
IR arguments, it also reports the parameters of callees the inliner merged
into~$F$, each from inside the inlined body, so inlining does not blind the
tool. The callbacks therefore pass no program counter: the kernel takes the
return address instead, which distinguishes the inlined bodies from each other
(Section~\ref{sec:ringbuf}).

\paragraph{Return Value Capture.} The pass scans~$F$'s blocks for
\texttt{ReturnInst} terminators and inserts
\texttt{\_\_sanitizer\_cov\_trace\_ret(size, val, offsets, num\_fields)}
before each. A \texttt{musttail} call must stay adjacent to the return that
forwards it, so those returns are skipped. A struct returned by value that the
ABI lowered to an indirect return---the IR function returns \texttt{void} and
writes through a hidden \texttt{sret} pointer---is reported by that buffer's
address, so an indirect return is not dropped; a struct the ABI returned in
registers has no address and is reported as its separate elements. Only~$F$'s
own frame is reported: an inlined callee has no return instruction left, and no
debug record describes a return value the way \texttt{DILocalVariable}
describes a parameter.

\paragraph{Edge Cases.} Functions without debug info, variadic parameters
beyond the declared list, and \texttt{naked} functions are skipped gracefully.
Argument indices are 0-based and follow the source parameter list; the hidden
\texttt{sret} pointer consumes no index. The pass is controlled by two
\texttt{cl::opt} flags, \texttt{-sanitizer-coverage-trace-args} and
\texttt{-sanitizer-coverage-trace-ret}, surfaced in the driver as
\texttt{-fsanitize-coverage=trace-args,trace-ret}.

\subsection{Lock-Free Per-Task Record Buffer}\label{sec:ringbuf}

The buffer is append-only rather than circular, which is worth stating plainly
because ``ring'' would imply the opposite failure mode: records accumulate from
\texttt{area[1]} upward, \texttt{area[0]} counts the words committed so far,
and once a record no longer fits it is dropped. A trace that outgrows the
buffer therefore loses its \emph{tail}, not its head---the beginning of an
execution is preserved, which is what a consumer reconstructing a call sequence
needs. This matches mainline \texttt{kcov}'s buffer discipline.

The kernel backend adds per-task fields to \texttt{task\_struct}:
\texttt{kcov\_df\_area} (pointer to the \texttt{u64} buffer),
\texttt{kcov\_df\_size} (capacity in words), \texttt{kcov\_df\_enabled},
\texttt{kcov\_df\_seq} (sequence counter plus recursion guard), and, for the
remote path, \texttt{kcov\_df} and \texttt{kcov\_df\_remote\_depth}.

\paragraph{Write Path.} The callback implementation uses
\texttt{READ\_ONCE}/\texttt{WRITE\_ONCE} to reserve a contiguous slot in
the buffer (portable to ARM64 without architecture-specific atomics), under the
same single-writer discipline as mainline \texttt{kcov.c}: the record length is
validated first and the word count at \texttt{area[0]} is committed only once
the record fits, so \texttt{area[0]} is always an exact high-water mark of
written words. If the record does not fit, the event is silently
dropped---no blocking, no allocation, no spinlock. The callbacks take no
program counter; the recorded PC is the callback's return address minus one
byte, so it lands inside the call instruction rather than on the instruction
after it. That matters because the compiler also reports the arguments of
inlined callees from inside each inlined body: an address one past the end of
such a body would name the next frame. The PC is then canonicalized by
subtracting the KASLR offset, as mainline \kcov{} does.

When \texttt{num\_fields} is zero the value arrived in a register and is stored
as it came---nothing is dereferenced. When it is non-zero, \texttt{val} is an
address and each field is read as
$\mathit{field\_addr} = \mathit{val} + \mathit{offsets}[2i]$ for
$\mathit{offsets}[2i+1]$ bytes, clamped to 8, via
\texttt{copy\_from\_kernel\_nofault()}. A \texttt{NULL} or
\texttt{IS\_ERR\_VALUE} address ($[-4095,-1]$), a field that cannot be read,
and a parameter the compiler reported with size~0 all store the sentinel
\texttt{KCOV\_DF\_MAGIC\_BAD}, so a missing value is distinguishable from a
genuine zero. The callbacks are bracketed by
\texttt{user\_access\_save()}/\texttt{restore()} so that a record written from
a function with SMAP/PAN user access enabled neither trips objtool nor leaves
user access open across the collector.

\paragraph{Record Format.} Each record is a variable-length run of
\texttt{u64} words: a three-word header followed by $\mathit{nvals}$ value
words, where $\mathit{nvals}$ is the number of expanded fields, or~1 when the
record carries the value itself. Word~[0] packs the sequence number
(bits 0--23), the record type (bits 28--31: \texttt{0xE} entry, \texttt{0xF}
return, \texttt{0xC} comparison), $\mathit{nvals}$ (bits 32--47), the argument
or return size in bytes (bits 48--55, clamped to 255), and the argument index
(bits 56--63, clamped to 255; zero for a return). Word~[1] is the PC. Word~[2]
is the address the field values were read from, and zero when the record
carries the value itself---so word~[2] also tells a consumer which of the two
shapes it is looking at (Figure~\ref{fig:record}). The field table itself never
reaches user space: it stays in \texttt{.rodata}, and the record carries only
the resulting values.

\paragraph{Unified stream.} When \texttt{CONFIG\_KCOV\_ENABLE\_COMPARISONS} is
also set, the shared \texttt{\_\_sanitizer\_cov\_trace\_cmp*()} callbacks fan
out into the same buffer as \texttt{0xC} records carrying both operands and the
\texttt{KCOV\_CMP\_SIZE()}/\texttt{KCOV\_CMP\_CONST} type bits, so
input-to-state operand pairs and boundary arguments arrive interleaved in one
sequence-numbered stream rather than in two buffers that must be correlated
afterwards.

\paragraph{Safety.} Callbacks are marked \texttt{notrace},
\texttt{\_\_no\_sanitize\_coverage}, and \texttt{noinline} to prevent recursion,
and bit~31 of \texttt{kcov\_df\_seq} is a per-task guard held for the duration
of a record so that instrumentation reached from inside the collector cannot
re-enter it. No \texttt{printk} or allocation occurs in the data path. The write
path bails out when \texttt{!in\_task() || pagefault\_disabled()}: the first
rejects softirq, hardirq, and NMI, and the second contains the
self-instrumentation storm that otherwise results when an instrumented leaf is
reached from inside a \texttt{copy\_from\_kernel\_nofault()} region---a single
KASAN stack walk would otherwise issue a callback per load.

\subsection{Separate Device Interface}\label{sec:device}

\toolname{} exposes \texttt{/sys/kernel/debug/kcov\_dataflow} as a device
\emph{completely independent} from the existing \texttt{/sys/kernel/debug/kcov}.
This ensures zero interference with syzkaller's existing KCOV usage.

The ioctl namespace uses magic~\texttt{'d'}:
\begin{itemize}[nosep]
  \item \texttt{KCOV\_DF\_INIT\_TRACK} (\texttt{\_IOR('d', 1, unsigned long)}):
        set the buffer size in \texttt{u64} words, by value, as
        \texttt{KCOV\_INIT\_TRACE} does
  \item \texttt{KCOV\_DF\_ENABLE} (\texttt{\_IO('d', 100)}): start recording
        into the calling task's own buffer
  \item \texttt{KCOV\_DF\_DISABLE} (\texttt{\_IO('d', 101)}): stop recording
  \item \texttt{KCOV\_DF\_REMOTE\_ENABLE} (\texttt{\_IOW('d', 102, \_\_u64)}):
        publish a \texttt{kcov\_remote\_handle()}-encoded handle so that kernel
        threads and other tasks annotated with
        \texttt{kcov\_df\_remote\_start()} record into this buffer; passed by
        pointer so the full 64-bit handle survives 32-bit and compat callers
  \item \texttt{KCOV\_DF\_REMOTE\_DISABLE} (\texttt{\_IO('d', 103)}): withdraw
        the handle
\end{itemize}
User-space maps the buffer via \texttt{mmap()} for zero-copy reads and walks it
as \texttt{pos += KCOV\_DF\_RECORD\_WORDS(nvals)} while
\texttt{pos < 1 + area[0]}. Remote writers assemble records in a private
per-worker scratch buffer and publish them into the shared area with a single
\texttt{atomic64\_try\_cmpxchg()} cursor update, so many kworkers can merge
without a lock.

\subsection{Rust Module Support}\label{sec:rust}

The Rust compiler (\texttt{rustc}) bundles its own LLVM (v23 for
rustc~1.101), which lacks my custom flags. Two instrumentation paths exist:

\paragraph{Path A: Post-compilation pipeline (no rustc modification).}
For environments using an unmodified rustc:
\begin{enumerate}[nosep]
  \item \texttt{rustc --emit=llvm-ir}: generate LLVM IR text with debug info
  \item \texttt{opt -passes=sancov-module -sanitizer-coverage-trace-args
        -sanitizer-coverage-trace-ret}: instrument with my pass
  \item \texttt{llc -filetype=obj}: compile to object code
  \item Standard module linking produces the instrumented \texttt{.ko}
\end{enumerate}
Step~2 needs no coverage level. It used to: the module pass returned
immediately when the coverage type was \texttt{SCK\_None}, so a direct
invocation without \texttt{-sanitizer-coverage-level} produced a cleanly
linking but entirely uninstrumented module, with no diagnostic. The driver
supplies a level when it parses \texttt{-fsanitize-coverage=}, which is why the
failure only appeared through \texttt{opt}. Since argument and return tracing
instrument function boundaries rather than blocks or edges, they are complete
without a level, so the pass now admits them under \texttt{SCK\_None}; every
block-level emission remains guarded by its own option, so nothing extra is
inserted.
This works because LLVM IR is language-agnostic: my pass operates identically
on Rust-generated IR (Figure~\ref{fig:rust-pipeline}). The text format (\texttt{.ll}) avoids bitcode version
incompatibilities between LLVM~23 and~24. Struct field expansion works on Rust
\texttt{\#[repr(C)]} types whose \texttt{DICompositeType} metadata is preserved
by \texttt{rustc} with debug info enabled.

\subsection{Pointer Dereference and Dynamic Struct Capture}\label{sec:deref}

A key design question is whether \toolname{} can capture struct fields from
dynamically allocated (heap) memory, not just stack-local values. The answer is
yes: the kernel callback performs \emph{one level of pointer dereference} at
runtime.

\paragraph{Mechanism.} When a function parameter is a pointer to a struct
(e.g., \texttt{struct session\_data *sd} where \texttt{sd} was
\texttt{kmalloc}'d), the LLVM pass emits the pointer value as the callback's
\texttt{val} operand together with the compile-time offset table. At runtime,
the callback computes each field address as
$\mathit{field\_addr} = \mathit{val} + \mathit{offsets}[2i]$ and reads
$\mathit{offsets}[2i+1]$ bytes via
\texttt{copy\_from\_kernel\_nofault()}. This works regardless of whether the
struct resides on the heap, stack, or in static memory.

\paragraph{Safety for edge cases:}
\begin{itemize}[nosep]
  \item \textbf{Freed slab (KASAN poison):} Safely reads poison bytes
        (\texttt{0xfd}/\texttt{0xff})---revealing the object was freed.
  \item \textbf{Unmapped page:} \texttt{copy\_from\_kernel\_nofault()} returns
        error; the field word is set to \texttt{KCOV\_DF\_MAGIC\_BAD}.
  \item \textbf{ERR\_PTR:} Detected via the \texttt{IS\_ERR\_VALUE} range check;
        the pointer is not dereferenced and every field word is
        \texttt{KCOV\_DF\_MAGIC\_BAD}.
  \item \textbf{NULL:} Same---detected, not dereferenced, marked.
  \item \textbf{Field wider than a word:} A field larger than 8 bytes is
        clamped to its low 8 bytes rather than skipped.
\end{itemize}

\paragraph{Design choice: shallow capture.} I perform exactly one level of
dereference (pointer $\to$ struct fields). I do \emph{not} chase pointers
inside the struct (e.g., a \texttt{char *buf} field stores the pointer value,
not the string contents). This bounds the cost to $O(n)$ where $n$ is the
number of struct fields, and avoids recursive faults on invalid nested pointers.
The pointer value itself is informative: NULL indicates freed/uninitialized,
\texttt{0xffff888...} indicates valid kernel heap, and KASAN poison patterns
indicate use-after-free.

\paragraph{Nested objects are not followed.} The field table is flat and
carries no types: a member that is itself a struct contributes a single
\emph{(offset, size)} pair for the bytes it occupies, and a member that is a
pointer to a struct contributes the 8 bytes holding the pointer. The compiler
unwraps exactly one \texttt{DW\_TAG\_pointer\_type} level, and only at the top:
a \texttt{struct inner *} member of a traced \texttt{struct outer} is reported
as an address, not expanded, even when the module already contains a field
table for \texttt{struct inner} because some other parameter had that type.
Combined with the 8-byte clamp, a nested composite member is therefore visible
only as its first word. Capturing a second level would require both a compiler
change (a table shape that can express nesting) and a kernel change (a bounded
recursive read), and the record format would have to grow a way to say which
table a run of value words belongs to.

\section{Implementation}\label{sec:impl}

\subsection{LLVM Pass ($\sim$710~LOC)}

The pass extends \texttt{SanitizerCoverage.cpp} with two entry points and a
set of debug-info helpers.

\texttt{InjectTraceForArgs(Function \&F, const DominatorTree \&DT)} first calls
\texttt{collectInlineFrames()}, which splits~$F$'s code into source-level
frames---$F$'s own, plus one per callee the inliner merged in---and, for each,
maps every \texttt{DILocalVariable} marked as a parameter back to the IR
value(s) holding it, respecting \texttt{DW\_OP\_LLVM\_fragment} splits. Each
frame is then reported by \texttt{injectTraceForFrame()}, which places the
calls at the frame's start, pushed down past the definition of every reported
value so each call is dominated by its operands and clamped back to a legal
insertion point.

Type resolution goes through three helpers:
\texttt{getDeclaredParamType()} and \texttt{getDeclaredReturnType()} read the
declared types out of the subprogram's type array
(\texttt{SP->getType()->getTypeArray()}), and
\texttt{getTracedStructType()} unwraps a single
\texttt{DW\_TAG\_pointer\_type} level to reach a \texttt{DICompositeType}.
\texttt{getFieldOffsets()} then walks that composite's \texttt{DW\_TAG\_member}
list, skipping static members and zero-sized members (a flexible array member
or an empty base class), widening a bitfield to the bytes that hold it, and
emits a private unnamed-address constant \texttt{\_\_sancov\_offsets\_} global
of $2N$ words. Results are memoized in \texttt{FieldOffsetsCache} keyed on the
\texttt{DICompositeType}, so one global serves every use of that type in the
module---there is no name hash and no type tag in the table.

\texttt{getReportedValue()} performs the widening to the callback's single
\texttt{i64} operand; \texttt{getReportedValues()} splits a first-class
aggregate the ABI passed in registers into its elements, each reported on its
own.

\texttt{InjectTraceForRet(Function \&F)} scans~$F$'s basic blocks for
\texttt{ReturnInst} terminators, skipping those that forward a
\texttt{musttail} call, and reports either the returned value, the pointee
fields of a returned pointer, or the \texttt{sret} buffer of an indirect
struct return.

Integration into the clang driver required changes to:
\begin{itemize}[nosep]
  \item \texttt{CodeGenOptions.def}: \texttt{SanitizeCoverageTraceArgs} and
        \texttt{SanitizeCoverageTraceRet} flags
  \item \texttt{SanitizerArgs.cpp}: parse \texttt{"trace-args"}/\texttt{"trace-ret"}
        (enum values $1\ll20$ and $1\ll21$), and the corresponding
        \texttt{-fsanitize-coverage-trace-args}/\texttt{-trace-ret} cc1 flags
  \item \texttt{BackendUtil.cpp}: wire to \texttt{SanitizerCoverageOptions}
  \item \texttt{Instrumentation.h}: add \texttt{TraceArgs}/\texttt{TraceRet}
        booleans
\end{itemize}
Unlike the other \sancov{} modes, \traceargs{} and \traceret{} satisfy the
``some mode was requested'' check on their own, so neither implies
\tracepc{}-guard instrumentation.

\subsection{Kernel Backend ($\sim$1170~LOC)}

The kernel implementation in \texttt{kernel/kcov\_dataflow.c} (a separate file
from the existing \texttt{kcov.c}, per reviewer request) adds:
\begin{itemize}[nosep]
  \item \texttt{struct kcov\_dataflow}: owns buffer, size, refcount, remote
        handle, and \texttt{file\_operations}.
  \item \texttt{\_\_sanitizer\_cov\_trace\_args(u32 arg\_idx, u32 arg\_size,
        u64 val, u64 *offsets, u32 num\_fields)}: marked \texttt{notrace},
        \texttt{\_\_no\_sanitize\_coverage}, \texttt{noinline}; wraps
        \texttt{kcov\_df\_write()} in
        \texttt{user\_access\_save()}/\texttt{restore()} and derives the PC
        from \texttt{\_RET\_IP\_ - 1}.
  \item \texttt{\_\_sanitizer\_cov\_trace\_ret(u32 ret\_size, u64 val,
        u64 *offsets, u32 num\_fields)}: same pattern with argument index~0.
  \item \texttt{kcov\_df\_write()}: the shared collector---context guard,
        per-task recursion guard, slot reservation, header packing, and either
        the single register value or the \texttt{num\_fields} nofault field
        reads.
  \item \texttt{kcov\_df\_trace\_cmp()}: reached from the shared
        \texttt{\_\_sanitizer\_cov\_trace\_cmp*()} callbacks when
        \texttt{CONFIG\_KCOV\_ENABLE\_COMPARISONS} is set, writing
        \texttt{0xC} records into the same buffer behind a static key.
  \item \texttt{kcov\_df\_remote\_start()}/\texttt{stop()} and
        \texttt{kcov\_df\_merge()}: per-worker scratch collection published
        into the shared area with an atomic cursor.
\end{itemize}

Both callbacks are added to objtool's \texttt{uaccess\_safe\_builtin[]} list,
like the existing \texttt{\_\_sanitizer\_cov\_trace\_cmp*()} entries.

Kconfig options \texttt{CONFIG\_KCOV\_DATAFLOW\_ARGS} and
\texttt{CONFIG\_KCOV\_DATAFLOW\_RET} (both depending on \texttt{CONFIG\_KCOV})
gate compilation.

\subsection{Build System Integration}

\texttt{scripts/Makefile.kcov} exports \texttt{CFLAGS\_KCOV\_DATAFLOW}
containing the sanitizer coverage flags, \texttt{RUSTFLAGS\_KCOV\_DATAFLOW}
containing the \texttt{-Cllvm-args=} equivalents for rustc, and
\texttt{CFLAGS\_KCOV\_DATAFLOW\_NO\_INLINE} separately.
\texttt{scripts/Makefile.lib} applies them when a module's Makefile declares:
\begin{lstlisting}
KCOV_DATAFLOW_my_module.o := y
\end{lstlisting}
The same per-file switch covers C and Rust objects, so a Rust module needs no
separate opt-in mechanism.

\paragraph{Global Enablement.}
\texttt{CONFIG\_KCOV\_DATAFLOW\_INSTRUMENT\_ALL} mirrors
\texttt{CONFIG\_KCOV\_INSTRUMENT\_ALL}: when enabled, all kernel objects are
compiled with dataflow instrumentation automatically. Individual files or
directories can opt out with \texttt{KCOV\_DATAFLOW\_file.o := n} or
\texttt{KCOV\_DATAFLOW := n}. This enables whole-kernel argument/return
extraction for comprehensive fuzzing campaigns.

\paragraph{Optional Inlining Control.}
\texttt{CONFIG\_KCOV\_DATAFLOW\_NO\_INLINE} (default \texttt{n}) adds
\texttt{-fno-inline} to files that opted in explicitly. It is not needed for
argument visibility---the pass reports the parameters of inlined callees from
inside each inlined body---but it keeps every frame a real call, which makes
the recorded PCs resolvable by \texttt{kallsyms} alone and keeps records
one-to-one with source call sites. The cost is increased stack depth and code
size, so it is suitable for targeted investigation sessions but not continuous
fuzzing. It deliberately does not extend to
\texttt{CONFIG\_KCOV\_DATAFLOW\_INSTRUMENT\_ALL}: building the whole kernel
with \texttt{-fno-inline} is not a supported configuration, because some code
relies on the inliner to fold a value into an inline-asm \texttt{"i"} operand
and fails to build without it.

For Rust modules built through Kbuild, no wrapper script is involved:
\texttt{RUSTFLAGS\_KCOV\_DATAFLOW} is appended by the same per-file switch
that handles C objects. The three-stage \texttt{opt}/\texttt{llc} pipeline of
Path~A applies only to modules built outside Kbuild.

\subsection{User-Space Runtime and libFuzzer}\label{sec:libfuzzer}

The same two callbacks have a user-space consumer, which keeps the ABI from
being a kernel-private interface. \texttt{compiler-rt} provides weak no-op
definitions in \texttt{sanitizer\_coverage\_libcdep\_new.cpp}, so a program
built with the flags links and runs without a runtime that implements them, and
libFuzzer provides real ones in \texttt{FuzzerTracePC.cpp}. Its
\texttt{HandleDataflow()} derives the PC the same way the kernel does---caller
return address minus one, for the same inlined-frame reason---drops records
whose \texttt{size} is~0, and folds each observed value into the value profile
keyed on the triple of call site, argument position, and field index, so the
same value seen at a different site stays a distinct observation. A return is
given the synthetic position \texttt{0xFFFF} so it cannot collide with an
argument of the same function.

Two independent clamps are worth noting because they differ from the kernel's.
libFuzzer caps the field loop at 32 fields and, like the kernel, truncates a
field wider than 8 bytes. More importantly, libFuzzer has the \emph{whole}
\texttt{offsets} table in process---it reads the same \texttt{.rodata} array
the compiler emitted---whereas the kernel record deliberately carries only the
resulting values, leaving offsets and sizes behind
(Section~\ref{sec:ringbuf}). The field table is therefore available to a
user-space consumer and not to a kernel one; closing that gap is a UAPI
question, not a compiler one.

\subsection{User-Space Consumer}

A minimal consumer opens \texttt{/sys/kernel/debug/kcov\_dataflow}, calls
\texttt{ioctl(KCOV\_DF\_INIT\_TRACK, size\_in\_words)} to size the buffer,
\texttt{mmap()}s it, enables recording with \texttt{ioctl(KCOV\_DF\_ENABLE)},
triggers the target kernel path, then walks the mapped buffer---reading
\texttt{area[0]} once and stepping record by record with
\texttt{KCOV\_DF\_RECORD\_WORDS(KCOV\_DF\_HDR\_NVALS(hdr))}---before calling
\texttt{ioctl(KCOV\_DF\_DISABLE)}. Because the PC is a return address inside
the call that produced the record, resolving it with
\texttt{addr2line -i} names an inlined callee, where \texttt{kallsyms} can only
name the function its code was merged into.

\subsection{Performance Overhead}

\paragraph{Measurement provenance.} Both measurements below were taken on the
toolchain of Section~\ref{sec:eval} by \texttt{bench.sh} in the repository,
which records the kernel, clang, rustc and commit of every run alongside the
numbers. An earlier version of this paper carried figures from linux-next
7.1.0-rc6 with clang/LLVM~23, measured against a micro-benchmark module that
was never carried into the in-tree suite, and predating the ABI of
Section~\ref{sec:llvm-pass}---so they could neither be reproduced nor
compared. Where the two disagree it is noted, because the disagreements are
informative.

Absolute values are not comparable with that earlier table: the kernel
version, the configuration and the syscall mix all differ. The percentages
are.

\paragraph{Cost per recorded value.} What has been re-measured on the current
toolchain is the quantity that transfers between workloads: the cost of
storing one record. Driving \texttt{eight\_struct\_args\_c}'s trigger on
kernel \texttt{7.3.0-rc5-next-20261001+} with clang~\texttt{24.0.0git}
(\texttt{ca763b76e2fd}) and rustc~1.101.0, x86-64 under KVM, with only that
module carrying arg/ret instrumentation, gives
$\mathbf{18}$--$\mathbf{21}$\,\textbf{ns per stored record} across four runs
(17.1, 18.3, 20.6 and 20.9\,ns; the overhead on the same runs ranged 65--75\%).
The spread is the honest precision available from a guest with eight vCPUs
sharing a host, and it is reported rather than narrowed to the most favourable
pair. The benchmark derives this by counting the records a run
actually stored rather than by assuming how many calls the trigger makes---an
assumption that was wrong by a factor of 16 when checked, which would have
inflated the per-record figure by the same factor.

The percentage overhead is deliberately not promoted to a headline, because it
is a property of record \emph{density} rather than of the instrumentation: the
same $\sim$20\,ns costs +75\% on this trigger, which crosses 10{,}587 recorded
boundaries and comparisons per iteration, and far less on a workload that
crosses fewer. Table~\ref{tab:perf} therefore reports the density beside the
latency. An earlier version of this paper quoted +8.3\% at 44 callbacks per
iteration with no density stated, which made the figure impossible to compare
against anything---including its own successor.

\subsection{Triage Capability}

For each captured boundary, the ENTRY/RET record provides: (1)~which argument
carried a value, identified by \texttt{arg\_idx} and, within a struct, by
position in the field table; (2)~whether a struct field changed across a call,
visible as a difference between the ENTRY record of a callee and the ENTRY
record of the next function to receive the same object---this is what makes the
\texttt{rust\_ffi\_contract} postcondition violation legible; and (3)~the order
in which boundaries were crossed, from the 24-bit per-task sequence number, with
the PC identifying the call site. Resolving that PC with \texttt{addr2line -i}
additionally names an inlined callee, which \texttt{kallsyms} cannot.

What the records do \emph{not} give is a call \emph{tree}: there is no caller
field and no depth counter, so \texttt{trigger-view.py} reconstructs nesting
heuristically from sequence order and symbol boundaries. A record also carries
no piece index, so two register pieces of one struct return are
indistinguishable from two calls to the same function
(Section~\ref{sec:eval}).

\subsection{Eight Struct Arguments, C and Rust}

To verify that \toolname{} captures Rust kernel module function arguments
natively (without the post-compilation pipeline), I built \texttt{rustc}
against the custom LLVM~24 containing the trace-args/ret passes. The kernel
build system passes \texttt{-Cllvm-args=-sanitizer-coverage-trace-args}
and \texttt{-Cllvm-args=-sanitizer-coverage-trace-ret} to rustc for modules
with \texttt{KCOV\_DATAFLOW\_module.o := y}.

The \texttt{eight\_struct\_args\_c} module and its Rust twin
\texttt{eight\_struct\_args\_rust} exercise three struct families, each with
eight members:
\begin{itemize}[nosep]
  \item \textbf{Flat} \texttt{s1..s8}: \texttt{sN} holds $N$ \texttt{u64}
        members side by side, and \texttt{sf\_N} takes $N$ struct pointers.
        This covers plain field expansion and, at \texttt{sf\_7}/\texttt{sf\_8},
        arguments the x86-64 ABI passes on the stack rather than in the first
        six registers.
  \item \textbf{Value-nested} \texttt{st1..st8}: \texttt{stN} embeds every
        smaller struct \emph{by value}, so \texttt{st8} is eight levels deep.
        Exercised on the stack.
  \item \textbf{Pointer-linked} \texttt{stp1..stp8}: every member is a pointer
        to a separately allocated object, so the nesting runs through the heap.
        Exercised with both \texttt{kmalloc} and \texttt{vmalloc} memory.
\end{itemize}
All fields carry the values $0\mathtt{x}11, 0\mathtt{x}22, \ldots$ (Figure~\ref{fig:eight-args}), and
\texttt{test\_modules.py} asserts each expanded field and every return value
(\texttt{sf\_N} returns $\sum_{k=1}^{N} 0\mathtt{x}11k$; the nested families
return \texttt{field0} plus the recursive sums of the embedded structs).

The two nested families are where the shallow-capture boundary of
Section~\ref{sec:deref} becomes observable rather than theoretical: the
value-nested tower yields one \emph{(offset, size)} pair per top-level member,
with an embedded struct clamped to its first word, and the pointer-linked tower
yields the pointer values rather than the objects behind them. The tests assert
exactly that, so the limitation is pinned down by the suite instead of being
left as an assumption.

\paragraph{Indirect struct returns.} \texttt{sf\_ret\_struct()} returns
\texttt{struct s4} by value. At $4 \times$~\texttt{u64}~=~32 bytes that is over
the register-return limit on both x86-64 and arm64, so the ABI returns it
indirectly through a caller-provided buffer---and \texttt{trace-ret} reports
that buffer the way it reports a struct argument: one value word per field,
word~[2] of the record holding the address the fields were read from, and
\texttt{size} the whole object rather than one field:
\begin{lstlisting}[language=,numbers=none,columns=fullflexible,basicstyle=\ttfamily\scriptsize,frame=none]
[RET] seq=.. sf_ret_struct+0x91 ret(32) @0xffff888000003000 = {0x11,0x11,0x22,0x33}
\end{lstlisting}
The runner asserts all four fields, the object size, \emph{and} that word~[2]
is non-zero---a scalar return leaves it zero, so that word is what
distinguishes the two record shapes. Checking only the first value word would
pass equally for a scalar return. \texttt{rsf\_ret\_struct()} takes the same
path from an \texttt{extern "C"} Rust function with a \texttt{\#[repr(C)]}
return type, and both modules are checked through one shared expectation---the
point of having both. A struct small enough to come back in registers
($\leq$~16 bytes here) has no address to report from and instead arrives as one
record per register piece with no field table; because the piece records carry
no piece index, a consumer cannot tell two pieces of one return from two calls
to the same function. That path is covered by the LLVM IR tests rather than by
the kernel suite.

\paragraph{\texttt{\#[repr(C)]} is load-bearing.} It is what makes the field
offsets the compiler reports match the C layout. A default-repr Rust struct may
be reordered, and the reported offsets would then describe that layout
instead---still correct, but not comparable with the C module field by field.

\subsection{Remote Capture from Kworker Context}

The \texttt{rust\_kworker\_remote} module exercises the remote path: the
trigger queues a work item on \texttt{system\_wq} whose three phases
(populate, update, drain of a composite store of red-black trees) run inside
\texttt{kcov\_df\_remote\_start()}/\texttt{stop()} on handle~1, which the
runner publishes with \texttt{KCOV\_DF\_REMOTE\_ENABLE}. The records land in
the enabling task's buffer even though they were produced by a kernel thread
that never entered a syscall, which is the gap that per-task-only collection
leaves open and that \texttt{ftrace}'s global patching fills only by also
capturing every other task on the system.

\section{Case Study: Runtime Boundary Auditing}\label{sec:realworld}

I applied \toolname{} to production kernel code to evaluate whether
boundary data-flow records provide actionable information beyond what
static review, KASAN, or edge coverage alone can surface.
I emphasize that the goal is \emph{demonstrating the methodology},
not claiming novel vulnerability discovery: several observations below
were subsequently clarified by Rust kernel community members as intentional behavior.

\subsection{Methodology}

For each target subsystem, I follow a four-step process:
\begin{enumerate}[nosep]
  \item Enable \texttt{KCOV\_DATAFLOW} on the target module
        (\texttt{KCOV\_DATAFLOW\_module.o := y}).
  \item Write a user-space program exercising boundary inputs (edge values,
        NULL pointers, maximum sizes).
  \item Capture the dataflow records via \texttt{mmap()} during execution.
  \item Run an \emph{automated contract verifier} that checks each captured
        $(\mathit{args}, \mathit{ret})$ pair against a contract database
        (Section~\ref{sec:contracts}).
\end{enumerate}

The key insight is that steps~3--4 require no human judgment for known
contracts: the verifier mechanically flags violations by comparing captured
values against pre/postcondition predicates. Only \emph{novel} violations
(functions without existing contracts) require manual analysis and maintainer
discussion. This shifts the workflow from ``report every observation and
wait for feedback'' to ``automatically verify known contracts; escalate only
confirmed anomalies.''

\paragraph{Why compile-time checking is insufficient.}
Rust's type system and C's \texttt{\_\_attribute\_\_} annotations enforce
structural constraints (correct types, lifetime bounds) but cannot verify
\emph{value} constraints that depend on runtime kernel state. A function
signature \texttt{alloc\_buf(size: u32)} type-checks for any \texttt{u32},
but at runtime the valid range depends on non-deterministic conditions:
available slab memory, per-task resource limits, concurrent allocations, and
RCU grace period state. These conditions are unknowable at compile time.
Boundary contract verification fills this gap: by capturing the \emph{actual}
argument values observed at runtime and checking them against value predicates
($\mathit{size} \leq \mathit{pool\_capacity}$), we verify invariants that
no static analysis or type system can express.

\emph{Critical distinction:} \toolname{} captures \emph{what the kernel
actually does} at runtime. Whether that behavior constitutes a bug requires
human judgment and maintainer confirmation---the tool provides evidence,
not verdicts.

\paragraph{Violation detection criteria.} A captured record is flagged as a
potential violation when any of the following hold:
\begin{enumerate}[nosep]
  \item An ENTRY argument value falls outside the documented or inferred
        valid range for that parameter (e.g., size $>$ buffer capacity).
  \item A RET value differs from what the precondition guarantees (e.g.,
        \texttt{from\_errno(-4096)} returns \texttt{-22} instead of
        propagating the input).
  \item A struct field changes between ENTRY and RET in a function documented
        as read-only with respect to that field.
  \item A pointer argument is \texttt{NULL} or in the \texttt{ERR\_PTR} range
        at a call site whose callee performs unconditional dereference.
\end{enumerate}
These criteria are applied offline against the captured buffer; the kernel
itself makes no policy decisions during recording.

\subsection{Observations and Kernel Community Responses}

\paragraph{Binder \texttt{SET\_MAX\_THREADS} (reported, not a bug).}
\toolname{} captured \texttt{BINDER\_SET\_MAX\_THREADS(0xffffffff)} being
accepted without bounds validation at
\texttt{drivers/android/binder/process.rs}'s ioctl dispatch. I initially
hypothesized this could
enable OOM via unbounded thread creation. Kernel maintainer Alice Ryhl
confirmed that this value does \emph{not} bypass \texttt{RLIMIT\_NPROC}:
the kernel enforces process-level thread limits independently. The recorded
dataflow correctly showed the ioctl accepting the value; the \emph{interpretation}
that this was exploitable was incorrect.

\paragraph{Binder \texttt{BC\_ENTER\_LOOPER} duplicate (reported, not a bug).}
Dataflow records showed a duplicate \texttt{BC\_ENTER\_LOOPER} command being
accepted at \texttt{drivers/android/binder/thread.rs}'s command loop. Rust
Kernel Community review confirmed the operation is bit-level idempotent
(\texttt{looper |= BINDER\_LOOPER\_STATE\_ENTERED}) and produces no corruption.

\noindent Both observations are on the \emph{Rust} binder: this tree carries no
C binder driver, only
\texttt{drivers/android/binder/}, gated on
\texttt{CONFIG\_ANDROID\_BINDER\_IPC\_RUST}. That is the substantive part
even though the findings themselves were refuted---the values were read out of
Rust frames at \texttt{-O2}, which is where \texttt{drgn} stops and where
ftrace's BTF-based printing cannot decode the arguments.

\paragraph{\texttt{Error::from\_errno} boundary (confirmed, pre-existing TODO).}
The dataflow record captured \texttt{from\_errno(-4096)} returning \texttt{-22}
(EINVAL). The source already contains a \texttt{// TODO: Make it a WARN\_ONCE}
comment acknowledging this edge case. This demonstrates \toolname{}'s ability
to surface known-but-unresolved issues through runtime evidence rather than
source inspection.

\subsection{Rust Kernel Core API Verification}

I exercised \texttt{rust/kernel/} APIs with boundary inputs to verify
correct behavior (not to find bugs). The dataflow records confirmed:

\begin{itemize}[nosep]
  \item \textbf{KVec:} \texttt{reserve(usize::MAX)} returns
        \texttt{AllocError}; \texttt{push\_within\_capacity}
        on a full vec returns the rejected value.
  \item \textbf{RBTree:} Duplicate key insert replaces the existing value
        (documented behavior, differs from \texttt{std::HashMap::try\_insert}).
  \item \textbf{Arc:} \texttt{into\_unique\_or\_drop} with multiple refs
        correctly drops; refcount operations captured at \texttt{-O2}
        where \texttt{drgn} cannot observe them.
  \item \textbf{Page:} Cross-page boundary reads rejected
        (offset+len $>$ 4096 $\to$ EINVAL).
  \item \textbf{UserSlice:} NULL, kernel-range, and unmapped addresses all
        return EFAULT correctly.
\end{itemize}

\noindent These results demonstrate that \toolname{} is equally valuable for
\emph{building confidence in correct implementations} as for identifying
potential issues. The dataflow records provide reproducible evidence that
APIs handle boundary inputs as intended---evidence that static review alone
cannot provide at \texttt{-O2}.

\paragraph{Reproducibility caveat.} These observations were made with ad-hoc
modules that were not carried into the in-tree selftest suite of
Section~\ref{sec:eval}. They are therefore not reproducible from the published
tree as it stands; only the four suite modules are. The one exception is
\texttt{RBTree}, which \texttt{rust\_kworker\_remote} exercises, though for the
remote-capture path rather than for duplicate-key semantics. Carrying the
remaining API probes into the suite is outstanding work.

\subsection{Correction Note}

In version~1 of this paper, I identified several potential vulnerabilities
in the Rust Android Binder driver and Rust kernel core APIs, assigning severity
labels (High, Critical) prior to maintainer verification. Following review
and discussion with the Linux kernel maintainers, these specific findings
were determined to be not exploitable under standard configurations or
addressed by existing kernel mitigations:

\begin{itemize}[nosep]
  \item \texttt{BINDER\_SET\_MAX\_THREADS(0xffffffff)}: not exploitable---
        \texttt{RLIMIT\_NPROC} enforcement is independent and prevents
        unbounded thread creation regardless of the stored value.
  \item \texttt{BC\_ENTER\_LOOPER} duplicate: not a corruption vector---
        the operation is bit-level idempotent.
  \item Rust API behavioral observations (e.g., \texttt{RBTree} duplicate
        key semantics): documented intentional behavior, not bugs.
\end{itemize}

\noindent Consequently, these findings have been removed from this version.
The system design, methodology, and the runtime boundary auditing framework
presented in the preceding sections remain valid. Verified findings will be
incorporated step by step in subsequent versions as maintainer review
completes.

\section{Why ftrace Does Not Replace Boundary Data-Flow}\label{sec:ftrace}

A natural question is whether existing tracing infrastructure (\texttt{ftrace},
\texttt{kprobes}, eBPF) could achieve similar results. It can reach part of the
way, and the gaps are architectural rather than incidental.

\paragraph{Global text patching, not per-task instrumentation.}
\texttt{ftrace}, \texttt{kprobes}, and eBPF all patch global kernel text, so a
probe fires on every task on every CPU. Per-task selection is a post-trigger
filter applied to a shared stream, not a property of the instrumentation.
\toolname{} records into the enabling task's own buffer, and follows that task
through \texttt{execve}---which is what makes a captured record a reproducible
per-input artifact rather than a slice of system-wide activity.

\paragraph{Six arguments, and no more.} ftrace's function-args feature is
capped at \texttt{FTRACE\_REGS\_MAX\_ARGS}, which is 6. Scanning the
\texttt{next-20260831} tree, 8{,}195 of 807{,}481 distinct functions (1.01\%)
declare more than six parameters, and ftrace truncates the 7th onward for every
one of them; the tail is long, reaching 33 parameters. Restricting the count to
functions that actually survive as a text symbol in one representative
\texttt{vmlinux}---the real ftrace targets---still leaves 668. The dataflow
callbacks have no such cap: they report one call per declared parameter.

\paragraph{Rust is only partially reachable.} \texttt{rustc} does emit
\texttt{\_\_fentry\_\_} stubs---\texttt{-Zinstrument-mcount} accepts
\texttt{fentry}, \texttt{fentry-record}, and \texttt{fentry-nop-record} on
supported targets---so the claim that Rust objects are simply unpatchable is
wrong. The gap is one level up: idiomatic Rust types (generics, slices, trait
objects) do not lower to the \texttt{repr(C)} shapes that
\texttt{pahole}/BTF-based argument printing expects, so even where the probe
site exists, the argument values are not decodable by the BTF machinery.
\toolname{} reads the types from DWARF at the IR level instead, before any of
that applies.

\paragraph{Inlined code has no boundary at all.} A callee the inliner merged
away leaves no \texttt{call} for ftrace to patch, and no
\texttt{\_\_fentry\_\_} stub; reaching it requires an explicit
\texttt{noinline} or \texttt{\#[inline(never)]} in the source. The dataflow
pass reports inlined callees' parameters from inside each inlined body
(Section~\ref{sec:llvm-pass}), and
\texttt{CONFIG\_KCOV\_DATAFLOW\_NO\_INLINE} can additionally keep the
boundaries themselves when a session wants one record per source call site.

\paragraph{Rust symbol mangling.} Rust function names are mangled into
unreadable strings (e.g., \texttt{\_RNvMs3\_NtCsgHKxaxYGgF6\_11rust\_binder...}).
Setting ftrace filters or kprobe targets requires these exact names, whereas
the dataflow pass instruments by compiler flag and needs no symbol list.

\paragraph{\toolname{} operates at LLVM IR level.} My pass runs on LLVM IR
\emph{before} codegen---the common representation shared by both \texttt{clang}
(C) and \texttt{rustc} (Rust). At this level, function arguments are explicit
SSA values with debug metadata, struct types have \texttt{DICompositeType}
annotations, and the optimizer has not yet destroyed variable locations. The
inserted callbacks survive optimization because they are function calls with
side effects. Table~\ref{tab:ftrace} summarizes the comparison.

\begin{table}[t]

\section{Boundary Contract Runtime Verification}\label{sec:contracts}

I observe that \toolname{} enables a new form of \emph{runtime verification}
for kernel functions: verifying pre/postcondition contracts at function
boundaries without source modification, for any function the monitored process
executes---including functions the developer did not anticipate.

\subsection{Functions as Black-Box Subsystems}

Every kernel function call is a boundary between a \emph{caller} (who provides
inputs) and a \emph{callee} (a black box from the caller's perspective):
$$\text{Caller} \xrightarrow{[\mathit{arg}_1, \ldots, \mathit{arg}_n]}
  f_{\text{callee}} \xrightarrow{[\mathit{ret}]} \text{Caller}$$

The caller cannot observe what happens inside the callee. It can only choose
arguments (precondition) and observe the return value (postcondition).
\toolname{} captures \emph{both sides} of this boundary, making the black box
transparent without modifying it.

\subsection{Formal Boundary Contracts}

Define a \emph{Boundary Contract} $\mathcal{C}(f) = (\mathcal{P},
\mathcal{Q})$ for function $f$:
\begin{itemize}[nosep]
  \item $\mathcal{P}(\mathit{args})$: precondition predicate over input arguments
  \item $\mathcal{Q}(\mathit{args}, \mathit{ret})$: postcondition predicate
        over return value given inputs
\end{itemize}

\noindent\textbf{Example:} For the Rust binder's
\texttt{Process::set\_max\_threads(max: u32)}, reached from
\texttt{ioctl\_write\_only()} on \texttt{BINDER\_SET\_MAX\_THREADS}:
\begin{align*}
\mathcal{P}&: \mathit{max} \leq \mathit{plausible\_thread\_cap} \\
\mathcal{Q}&: \mathit{inner.max\_threads} = \mathit{max}
\end{align*}

A \emph{contract violation} occurs when the caller passes arguments violating
$\mathcal{P}$ (caller bug) or the callee returns values violating $\mathcal{Q}$
given valid inputs (callee bug). Section~\ref{sec:realworld} reports what
happened when I actually wrote this predicate: the capture was correct and the
predicate was wrong---\texttt{set\_max\_threads()} storing an arbitrary
\texttt{u32} is harmless because \texttt{RLIMIT\_NPROC} is enforced elsewhere.
A contract database is only as good as its predicates, which is why the tool
reports evidence and not verdicts.

\subsection{Struct Member Contract Verification}\label{sec:struct-contract}

Beyond scalar argument bounds, \toolname{}'s automatic struct field expansion
enables \emph{struct member contracts}: predicates over relationships between
fields that must hold for a function's internal logic to operate correctly.

\paragraph{The problem.} Most kernel functions receive struct pointers whose
fields encode complex state (flags, sizes, pointers, reference counts). The
function's internal logic assumes these fields satisfy certain relationships
(e.g., \texttt{buf\_len $\geq$ data\_offset + data\_size}). These
relationships are typically enforced by conditional checks inside the function,
but:
\begin{itemize}[nosep]
  \item Checks may be missing for uncommon field combinations.
  \item Concurrent modification may invalidate a field between the check and
        its use (TOCTOU).
  \item The caller may construct a struct in an inconsistent state that passes
        individual field validation but violates cross-field invariants.
\end{itemize}

Compile-time type systems cannot detect these: the struct is well-typed
regardless of whether its fields are internally consistent. The correct state
depends on runtime conditions (which allocator path was taken, whether a lock
is held, what RCU grace period is active).

\paragraph{Formalization.} Extend the boundary contract to include a
\emph{struct consistency predicate} $\mathcal{S}$ over fields of a struct
parameter:
$$\mathcal{S}(\mathit{fields}): \bigwedge_i \phi_i(f_1, f_2, \ldots, f_n)$$

\noindent\textbf{Example:} For \texttt{smb2\_create\_req *req}:
\begin{align*}
\mathcal{S}&: \mathit{req.NameLength} \leq \mathit{req.BufferLength} \\
           &\wedge\ \mathit{req.CreateContextsOffset} + \mathit{req.CreateContextsLength}
              \leq \mathit{req.StructureSize}
\end{align*}

\paragraph{Detection mechanism.} At function entry, \toolname{} captures all
struct fields simultaneously, one record per parameter
(Figure~\ref{fig:struct-verify}). The offline
verifier evaluates $\mathcal{S}$ over the captured field values. A violation
means the function received a struct whose internal state is inconsistent with
what its logic requires---either the caller constructed it incorrectly, or
concurrent modification corrupted it between construction and use.

\paragraph{Concrete example.} Consider a kernel network handler:
\begin{lstlisting}[numbers=none]
[ENTRY] process_msg(struct{.hdr_len=20, .payload_len=4096,
                           .total_len=100, .flags=0x3})
\end{lstlisting}
Contract: $\mathit{hdr\_len} + \mathit{payload\_len} \leq \mathit{total\_len}$.
Captured: $20 + 4096 = 4116 > 100$ --- violation. The function will either
read out-of-bounds or silently produce incorrect output. No crash occurs
(the buffer may be large enough by coincidence), no KASAN report fires,
and edge coverage sees the same path regardless of field values.

\paragraph{Why this matters.} These bugs are among the hardest to find:
\begin{itemize}[nosep]
  \item They produce no immediate crash (data is read, just incorrectly).
  \item Sanitizers do not fire (the access is technically in-bounds of the
        allocation, just semantically wrong).
  \item Static analysis cannot reason about runtime struct state.
  \item They often manifest only under specific timing or workload conditions.
\end{itemize}
Struct member contract verification with \toolname{} detects these violations
at runtime with zero source annotation, by comparing the actual field values
against the cross-field predicates that the function's conditional logic
implicitly assumes. An eBPF program with a hand-written per-function reader can
reach the same values; what \toolname{} removes is the per-function work, since
the field layout comes from the compiler rather than from the analyst.

\paragraph{Formal model.}
Let a function $f$ receive a struct parameter $s$ with fields
$(f_1, \ldots, f_n)$. Define the \emph{structural verification predicate}:
$$\mathcal{V}(f) = \mathcal{S}(f_1, \ldots, f_n)$$
where $\mathcal{S}$ encodes cross-field invariants that must hold for the
function's logic to operate correctly
(e.g., $\mathit{len} \leq \mathit{cap}$,
$\mathit{offset} + \mathit{size} \leq \mathit{total}$).

\noindent A \emph{violation} $\neg\mathcal{V}(f)$ at function entry means the
function's internal conditional logic will either:
\begin{enumerate}[nosep]
  \item Take an unanticipated branch (missing check $\to$ silent corruption), or
  \item Produce semantically incorrect output (wrong branch $\to$ logic bug).
\end{enumerate}

\paragraph{Scope of capture.} \toolname{} captures struct fields reached
through pointer arguments via one level of dereference
(Section~\ref{sec:deref}). It does \emph{not} capture global kernel state
(e.g., slab pressure, lock state) unless that state is passed as an explicit
function argument. The verification predicate $\mathcal{S}$ is therefore
limited to relationships between fields \emph{within the same struct}---which
is precisely where most silent bugs reside, since the kernel trusts that
callers construct structs consistently.

\paragraph{Classification of violations.}
\begin{center}
\small
\begin{tabular}{@{}lll@{}}
\toprule
\textbf{Violation type} & \textbf{Predicate} & \textbf{Consequence} \\
\midrule
Cross-field overflow & $\mathit{off} + \mathit{len} > \mathit{cap}$ & OOB read/write \\
Length inconsistency & $\mathit{hdr} + \mathit{payload} > \mathit{total}$ & Truncation/overread \\
Flag-field mismatch & $\mathit{flags} \wedge F \neq 0 \wedge \mathit{ptr} = 0$ & NULL deref \\
Size exceeds bound & $\mathit{req\_sz} > \mathit{max\_allowed}$ & Allocation overflow \\
\bottomrule
\end{tabular}
\end{center}

\subsection{Toward Post-Mortem Formal Verification}\label{sec:postmortem}

Classical formal verification proves properties for \emph{all} inputs
statically, but is intractable for 30M~LOC kernels. I observe that
\toolname{}'s structured output enables a complementary approach:
\emph{post-mortem contract verification}---mechanically checking recorded
execution against formal specifications after the fact.

\paragraph{Key Insight.} The record buffer produces a complete sequence of
$\langle \mathit{PC}, \mathit{args}, \mathit{ret} \rangle$ tuples for every
instrumented function the process executed. This is a \emph{finite execution
trace} in the formal methods sense---the input to a runtime verification
monitor.

\paragraph{What This Enables.}
\begin{enumerate}[nosep]
  \item \textbf{Offline model checking:} Replay the buffer against temporal
        logic specifications (e.g., LTL: ``every \texttt{alloc} is eventually
        followed by \texttt{free} with the same pointer'').
  \item \textbf{Contract refinement:} Automatically infer likely contracts from
        many executions (Daikon-style invariant detection on kernel functions),
        then flag violations in new runs.
  \item \textbf{Differential verification:} Compare argument/return value
        distributions across kernel versions to detect semantic regressions
        that pass all tests but violate implicit contracts.
\end{enumerate}

\paragraph{Soundness Boundary.} This is \emph{not} full formal verification:
it only covers paths actually exercised. However, combined with a fuzzer that
maximizes path diversity, it approaches bounded model checking---verifying
contracts over all \emph{reachable} states discovered during exploration.
The structured, machine-readable output (unlike \texttt{printk} logs) makes
this amenable to automated reasoning tools without manual log parsing.

\paragraph{Key property.} The dataflow records are a \emph{deterministic
artifact}: given the same kernel build, the same user action produces the same
records. Any party can independently reproduce and verify the analysis,
satisfying the reproducibility requirement for empirical security research.

\paragraph{Dual utility.} As Figure~\ref{fig:dual} shows, the same records
serve both (1)~security auditing
(identifying argument values that violate API contracts) and (2)~guided fuzzing
(constraining mutation to value ranges observed at deep kernel code paths,
eliminating blind 64-bit enumeration).

\paragraph{Implication for AI-assisted auditing.} Without runtime evidence,
AI-based code review produces hypotheses that may be incorrect (as demonstrated
by my initial binder claims refuted by maintainers). With \toolname{}, the AI
analyzes observed records rather than speculating about behavior---findings are
grounded in physical execution regardless of reasoning quality.

\paragraph{Debug Info Requirement.} Struct field expansion needs
\texttt{CONFIG\_DEBUG\_INFO}, which both Kconfig options depend on, so this is
enforced at configuration time rather than degrading at runtime. For a
translation unit compiled without \texttt{-g}---which can happen for an
out-of-tree module---the pass still reports register-resident values, but
pointer arguments lose their field tables and an indirect struct return is
dropped entirely. Within the kernel the requirement is not a practical
constraint, since the DWARF options are already standard in fuzzing
configurations.

\paragraph{Rust Pipeline.} Dataflow tracking of Rust kernel modules requires
building \texttt{rustc} against the custom LLVM~24 that contains the
trace-args/ret passes. The post-compilation pipeline (Path~A) serves as a
proof-of-concept demonstrating language-agnosticism but cannot instrument
modules built through Kbuild. I propose adding native
\texttt{-Zsanitizer-coverage=trace-args} support to upstream rustc as future
work to eliminate the custom build requirement.

\paragraph{Buffer Overflow.} If instrumented code generates more events than
the buffer capacity, events are silently dropped. This is by design: the
collector runs with a per-task recursion guard held and must not sleep,
allocate, or take a lock, so there is nothing it could usefully block on. The
word count at \texttt{area[0]} is an exact high-water mark, so a consumer can
detect saturation by observing it pinned at capacity rather than by finding a
truncated record.

\paragraph{Interrupt, NMI, and nofault Context.} Instrumentation callbacks bail
out when \texttt{!in\_task() || pagefault\_disabled()}: a call originating from
a softirq, hardirq, or NMI handler is silently discarded, and so is one issued
from inside a \texttt{copy\_from\_kernel\_nofault()} region.
The first half is stricter than the per-context filtering used by mainline KCOV
(which allows softirq tracing via \texttt{kcov\_remote\_start}); I chose
the stricter policy because the dataflow callback performs pointer
dereferences (\texttt{copy\_from\_kernel\_nofault}) whose latency is
unacceptable in hard-interrupt paths, and because per-task buffer
interleaving from nested contexts would corrupt record boundaries.
The second half is a containment measure rather than a policy: an instrumented
leaf reached from inside the collector's own nofault read---or from a KASAN
stack walk---otherwise issues a callback per load and soft-locks the CPU, and
the per-task recursion guard only covers re-entry nested inside our own
callback, not a fresh entry from the unwinder. The trade-off is that records
are also dropped inside unrelated \texttt{pagefault\_disable()} regions
(\texttt{kmap\_atomic()} on HIGHMEM, futex and perf callchain probes), which
are short and rare on the targeted workloads.
Kernel threads are still reachable: \texttt{kcov\_df\_remote\_start()}
annotations let a kworker record into a published remote handle, as mainline
\kcov{} does, but only in sleepable task context---it takes a mutex---so it
closes the kworker gap and not the softirq one.
Bugs triggered exclusively from interrupt context are therefore invisible
to \toolname{}; however, such bugs are also unreachable by KCOV-guided
fuzzers, which exercise kernel code through syscalls in process context.

\paragraph{Fuzzer Integration.} A user-space consumer already exists: libFuzzer
implements both callbacks and folds the observed values into its value profile
(Section~\ref{sec:libfuzzer}). Syzkaller integration is the remaining work and
is a transport question rather than an instrumentation one---the executor must
parse the \texttt{mmap}'d \texttt{kcov\_dataflow} buffer and hash argument
values into the coverage bitmap. I envision a composite feedback signal: unique
$(\mathit{PC}, \mathit{arg\_hash})$ pairs provide finer-grained state
discrimination than unique edges alone. The interleaved \texttt{0xC} comparison
records in the same buffer give input-to-state matching for free once that
parsing exists.

\paragraph{Upstream Path.} The LLVM pass has been submitted as a pull
request\footnote{\url{https://github.com/llvm/llvm-project/pull/201410}} with
an RFC on LLVM
Discourse\footnote{\url{https://discourse.llvm.org/t/rfc-sanitizercoverage-add-fsanitize-coverage-trace-args-trace-ret/91026}};
LLVM maintainers have requested a formal RFC per the LLVM RFC
process\footnote{\url{https://llvm.org/docs/RFCProcess.html}} given the
complexity of extending \sancov with a new instrumentation mode, and that
review is ongoing. The kernel side was posted as RFC
v2\footnote{\url{https://lore.kernel.org/all/20260611-b4-kcov-dataflow-v2-v2-0-0a261da3987c@est.tech/}}
and now stands at v4---eight patches: the kcov core, the
\texttt{Documentation/dev-tools/kcov-dataflow.rst} description, four selftests,
and the \texttt{trigger-view.py} consumer---with the ksmbd remote-coverage
support carried separately. It remains an RFC deliberately: the kernel-side
design and the UAPI are being reviewed in parallel with the LLVM work rather
than after it, since the record format is the part that would be hardest to
change later.

\section{Related Work}\label{sec:related}

\paragraph{Coverage-Guided Kernel Fuzzing.}
syzkaller~\cite{vyukov2015syzkaller} and kAFL~\cite{schumilo2017kafl} use
edge/block coverage as feedback. DIFUZE~\cite{corina2017difuze} adds
interface-aware generation but no runtime data-flow.
MORPHUZZ~\cite{bulekov2022morphuzz} fuzzes virtual devices without data-flow
context. HEALER~\cite{sun2021healer} and
Rtkaller~\cite{ma2022rtkaller} learn relation models between syscalls to
construct deeper sequences, yet both remain blind to argument values and
plateau once the structural path space is exhausted.
SyzVegas~\cite{wang2021syzvegas} applies multi-armed bandit algorithms to
syzkaller's mutation strategy but still uses edge coverage as the sole reward
signal. ACTOR~\cite{fleischer2023actor} targets concurrency bugs via
schedule-aware fuzzing; its feedback is scheduling order, not data-flow.
Moonshine~\cite{pailoor2018moonshine} distills seeds from system call traces
to improve initial coverage but cannot guide mutation once coverage saturates.
Google's AIxCC kernel fuzzing approach~\cite{google2024aixcc} combines AFL
with KCOV and KASAN in a QEMU harness, reporting that ``the vulnerability
cannot be easily found even after hours of fuzzing, unless provided with seed
inputs close to the solution''---confirming that edge coverage alone saturates
on complex kernel targets.
All of the above rely solely on control-flow coverage; none capture the
argument values that drive state-dependent behavior.

\paragraph{Data-Flow Guided Fuzzing.}
Payer~\cite{payer2019dataflow} argues for data-flow-guided fuzzing but provides
no kernel implementation. Angora~\cite{chen2018angora} uses byte-level taint for
user-space programs at 10$\times$ overhead.
GREYONE~\cite{gan2020greyone} combines taint with coverage but targets
user-space only. Both pay an order-of-magnitude cost for byte-level precision.
\toolname{} makes the opposite trade: it observes values only where they cross
a function boundary, which is far less than full taint but costs a bounded
number of callbacks per call rather than a shadow operation per byte.

\paragraph{Kernel Instrumentation.}
KCOV~\cite{vyukov2016kcov} provides edge coverage---my foundation---and its
\texttt{trace-cmp} mode provides comparison operands, which \toolname{} reuses
rather than duplicates: when both are configured the operand pairs land in the
same buffer as the boundary records. \texttt{ftrace}, \texttt{kprobes}, and
eBPF patch global kernel text, so a probe fires for every task on every CPU and
per-task selection is a filter rather than a property of the instrumentation;
ftrace's argument printing is additionally capped at six parameters and depends
on BTF shapes that idiomatic Rust types do not produce
(Section~\ref{sec:ftrace}).

\paragraph{Post-Mortem Analysis.}
\texttt{drgn}~\cite{drgn} enables programmable vmcore analysis but requires a
crash and fails on optimized Rust code. \texttt{kdump}/\texttt{crash} provide
full memory dumps but require manual analysis and miss silent bugs.

\medskip\noindent
\toolname{} is the first system combining compile-time data-flow instrumentation
with a production-grade kernel transport, supporting both C and Rust, at a
measured 18--21\,ns per recorded value and +66\% syscall latency with the
whole kernel instrumented and collection idle
(Section~\ref{sec:eval}). The same two callbacks are also implemented by a
user-space libFuzzer runtime, so the instrumentation is a general
SanitizerCoverage mode rather than a kernel-specific mechanism.

\section{Conclusion}\label{sec:conclusion}

I presented \toolname{}, bridging the semantic gap between coverage-guided
fuzzing and data-flow analysis for OS kernels. My key insight is that function
boundaries are natural observation points where data-flow context is both cheap
to capture and highly informative for both automated exploration and human
triage.

The system requires no source annotation, operates safely in sleepable task
context with explicit rejection of interrupt, NMI, and nofault callbacks,
reaches kernel threads through a remote-handle path, and---uniquely---decodes
Rust kernel module arguments via both a post-compilation
pipeline and native instrumentation through a custom-built rustc. That last
point is narrower than it may appear: \texttt{ftrace} can place a probe in a
Rust object, but cannot decode idiomatic Rust argument types, and
\texttt{drgn} cannot read them at all once \texttt{-O2} has elided the DWARF
variable locations.

I demonstrated correctness with an in-tree selftest suite covering struct field
expansion in both C and Rust, arguments past the ABI's register budget,
indirect struct returns, a postcondition violation that produces no crash, and
capture from kworker context---showing that boundary data-flow context provides
information unavailable through any combination of KASAN, drgn, and edge
coverage. The same two callbacks also back a user-space libFuzzer consumer, so
the ABI is not kernel-specific.
Source code is available at \anonrepo{}.

\section{LLVM Pass: InjectTraceForArgs Pseudocode}\label{app:pass}

\begin{algorithmic}[1]
\Function{InjectTraceForArgs}{$F$, $\mathit{DT}$}
  \State $\mathit{SP} \gets F.\mathrm{getSubprogram()}$
  \If{$\mathit{SP} = \mathrm{null}$} \Return \EndIf
  \State $\mathit{Frames} \gets \Call{CollectInlineFrames}{F, \mathit{DT}}$
    \Comment{$F$'s own frame, then each inlined callee}
  \For{each $\mathit{Frame} \in \mathit{Frames}$}
    \State $\mathit{IP} \gets \mathit{Frame}.\mathrm{Start}$
      \Comment{pushed past every reported value's definition}
    \For{each declared parameter index $i \in 1 \ldots n$ of $\mathit{Frame}$}
      \State $V \gets \mathit{Frame}.\mathrm{Params}[i]$
        \Comment{IR value(s) from \texttt{DILocalVariable::getArg()}, 1-based}
      \State $T \gets \Call{GetDeclaredParamType}{\mathit{Frame}.\mathrm{SP}, i}$
      \State $\mathit{whole} \gets V$ is the entire parameter, not an ABI fragment
      \If{$\mathit{whole}$ \textbf{and} $V$ is a pointer \textbf{and}
          $\Call{GetFieldOffsets}{T}.\mathrm{Table} \neq \mathrm{null}$}
        \State $\mathit{Off} \gets \Call{GetFieldOffsets}{T}$
          \Comment{cached; unwraps one pointer level}
        \State \Call{Emit}{$i$, ptrtoint($V$), $\mathit{Off}$.ObjectSize, $\mathit{Off}$}
      \Else
        \For{each $(w, \mathit{sz}) \in \Call{GetReportedValues}{V}$}
          \State \Call{Emit}{$i$, $w$, $\mathit{sz}$, $\varnothing$}
            \Comment{$\mathit{sz}=0$ when $V$ is unreportable}
        \EndFor
      \EndIf
    \EndFor
  \EndFor
\EndFunction
\Statex
\Function{Emit}{$i$, $\mathit{val}$, $\mathit{size}$, $\mathit{Off}$}
  \State emit \texttt{trace\_args($i-1$, $\mathit{size}$, $\mathit{val}$, $\mathit{Off}$.Table, $\mathit{Off}$.NumFields)}
    \Comment{the ABI's \texttt{arg\_idx} is 0-based}
\EndFunction
\end{algorithmic}

\noindent Two details a reimplementation would otherwise get wrong. The
parameter index is 1-based inside the pass, because that is what
\texttt{DILocalVariable::getArg()} returns, and is decremented on the way into
the callback, whose \texttt{arg\_idx} is 0-based. And no \texttt{alloca} is
created: a value the ABI kept in a register is widened in place and passed in
one. \Call{GetFieldOffsets}{} emits a private constant
\texttt{\_\_sancov\_offsets\_} array of $2N$ words---$N$ consecutive
\emph{(offset, size)} byte pairs with no type tag---memoized per
\texttt{DICompositeType}, and is only consulted on the path that uses it, so a
struct that ends up reported by value leaves no unreferenced global behind.

\section{Record Buffer Format}\label{app:ringbuf}

Each record occupies $3 + \mathit{nvals}$ quadwords (64-bit each), where
$\mathit{nvals}$ is the number of expanded fields, 1 when the record carries
the value itself, and 2 for a comparison record:

\begin{center}
\small
\begin{tabular}{|c|l|p{10.0cm}|}
\hline
\textbf{Offset} & \textbf{Field} & \textbf{Description} \\
\hline
0 & \texttt{header} & \texttt{arg\_idx} [63:56] | \texttt{size} [55:48] | \texttt{nvals} [47:32] | \texttt{type} [31:28] | \texttt{seq} [23:0] \\
1 & \texttt{pc} & Call site that produced the record: callback return address $-1$, KASLR offset removed \\
2 & \texttt{address} & ENTRY/RET: address the fields were read from, 0 when the record carries the value itself. CMP: comparison type bits \\
3..3+\textit{nvals} & \texttt{val[\,]} & The value itself, the expanded fields, or the two CMP operands; \texttt{KCOV\_DF\_MAGIC\_BAD} (\texttt{0xBADADD85}) where there was nothing to record \\
\hline
\end{tabular}
\end{center}

\noindent Record types are \texttt{0xE} (entry), \texttt{0xF} (return), and
\texttt{0xC} (comparison). \texttt{size} and \texttt{arg\_idx} are clamped to
255, \texttt{nvals} to $2^{16}-1$. \texttt{area[0]} holds the number of record
words committed after it; every counted word has been written, so a consumer
walking \texttt{pos += 3 + nvals} while \texttt{pos < 1 + area[0]} stays inside
the mapping. The field \emph{table} is not part of the record: offsets and
sizes stay in kernel \texttt{.rodata} and never reach user space.

\section{Rust Post-Compilation Pipeline}\label{app:rust}

\begin{lstlisting}[language=bash,caption={Rust module instrumentation pipeline}]
