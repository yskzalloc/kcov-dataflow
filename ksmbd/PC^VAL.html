Coverage, but with a memory of what flowed
PC⊕VAL

How a Linux kernel fuzzer turns “which line of code ran” into “which line ran, carrying which value” — and why that one XOR is the difference between a fuzzer that gets bored and one that keeps digging.

01The problem

The lamplighter who runs out of streets

Picture a fuzzer as a lamplighter walking through a city — the city being all the code inside a program. Every street is a branch in the code. The lamplighter's job: light a lamp on every street he manages to walk down. The wall of lit lamps is his coverage map, and it's how he judges progress. A test input that lights a brand-new lamp was interesting — keep it, mutate it, walk further. An input that lights nothing new gets thrown away.

This is edge coverage, the idea behind AFL and, in the kernel, behind kcov + syzkaller. It works astonishingly well… until the wall fills up. Once the lamplighter has walked every reachable street, every input lights zero new lamps. He's technically still working, but he's bored: he can't tell a boring input from a dangerous one, because both light the same already-lit lamps.

Here's the catch that matters for finding bugs. A function like smb2_read(len, offset) is one street. Walking it with len = 8 and walking it with len = 0xFFFFFFFF lights the same lamp — yet only one of those is going to smash something. Edge coverage is value-blind. It sees where you went, never what you carried.

02The idea

Give every lamp a combination lock

The fix is deceptively small. Instead of one lamp per street, wire each lamp to a combination lock that takes two numbers: the street address (the program counter, PC — where in the code we are) and the cargo (the runtime value that flowed through that spot — an argument, a struct field, a return value).

The combination that picks which lamp lights is simply:

PC  ⊕  value  →  which lamp

Now the coverage map no longer records a set of places {PC}. It records a set of place–value pairs {(PC, value)}. Same street, same cargo → same lamp → nothing new, as before. But same street, new cargo → a different lamp lights → the fuzzer registers a discovery and keeps the input that produced it. Suddenly “walk smb2_read with a monstrous length” is a genuinely new frontier, not a re-run.

PC — the street address

The program counter of the instrumented call site. It answers where the data landed in the code. On its own, this is ordinary edge coverage — and it saturates.

VAL — the cargo

The actual bytes the kernel handled there: a length, a flags field, an offset, a return code. It answers what flowed. Folding it in gives the map a second axis that doesn't saturate while inputs keep varying.

Why XOR specifically, and not, say, addition or concatenation? Three reasons a systems programmer cares about: it's a single cheap instruction; it mixes all the bits of both operands into the result; and it keeps a little locality — a small change in the value nudges the lamp, so related values cluster instead of scattering into pure noise. (The real code follows the XOR with a multiply to fully shuffle the bits — more on that below.)

03Where the numbers come from

The kernel just writes down what it saw

An important design choice: the kernel does no folding at all. The compiler (a custom Clang pass) inserts callbacks at function entries and returns — __sanitizer_cov_trace_args and __sanitizer_cov_trace_ret — and those callbacks dump raw records into a shared ring buffer that userspace reads. Each record is just: a small header, the PC, some metadata, and the value(s) observed.

/* one record in the shared ring — kernel/kcov_dataflow.c */
area[i]     = type_marker | ((nfields) << 24) | seq;  // 0xE=args 0xF=ret 0xC=cmp
area[i + 1] = pc;                                // raw program counter, untouched
area[i + 2] = meta;                              // source arg_idx | size | ptr
area[i + 3] = value;   // a scalar, OR up to N struct fields

The arg_idx packed into that metadata word is worth a second look, because it's the one number the kernel copies through untouched and the harness later keys features on. It's the source-level parameter number — the len in smb2_read(len, offset) is argument 0, always — not the position of a machine register in the lowered calling convention. The compiler earns that: it recovers the source→IR mapping from debug info (DILocalVariable::getArg(), which the frontend stamps before the ABI rewrites anything), so a hidden struct-return pointer or a C++ this handle inserted ahead of the real arguments never shifts the numbering. The kernel never sees that complexity — the meaning of arg_idx was fixed at compile time, which is what makes a (PC, arg_idx, value) feature stable to fold on.

The same discipline is what lets the kernel stay dumb about structs. When an argument carries a struct, the Clang pass also emits the struct's [offset, size] field table, and the kernel walks it with copy_from_kernel_nofault (a fault-safe read) to record several fields per argument — so a length buried three fields deep in a request struct becomes its own piece of cargo. The kernel only ever sees one shape here — a pointer plus that table — but the compiler feeds it from three: a genuine pointer-to-struct argument; a small by-value struct the ABI smeared across registers or coerced to an integer, which the pass reassembles (from its DW_OP_LLVM_fragment pieces) back into a stack slot in source layout; and a struct return lowered to a hidden sret buffer, traced through that buffer so nothing is dropped just because the value came back indirectly. All the ABI variety is resolved compiler-side; the kernel reads defensively and uniformly — a bad pointer or a field it can't fault in yields a 0xBADADD85 sentinel instead of a crash.

Why raw? Keeping the fold out of the kernel means the policy — how aggressively to reward values, how to split the map, whether to run value-blind at all — lives in the userspace harness where it can be changed and A/B-tested without rebooting into a new kernel.
04The fold

Two neighborhoods on one wall

Userspace reads the raw records and “develops” them onto the coverage bitmap that libFuzzer actually watches — an array of counters called ctr[]. The clever part is that the wall is split into two neighborhoods:

The PATH region (left). Here only the PC matters — pure edge coverage. It fills up fast and then saturates, exactly like the bored lamplighter. That's fine: its job is to credit reaching code at all.

The VALUE region (right). Here the PC ⊕ VAL fold lands, and a lamp lights only the first time a given (PC, field, value) combination is ever seen — tracked by a 65,536-bit “have I seen this?” bitmap called val_seen.

/* grain/common.h — fb(): develop raw records onto ctr[] */
uint64_t h = pc * 0x517cc1b727220a95;         // spread the PC
ctr[(h >> 12) % path_n]++;                 // PATH region: value-blind, saturates

for (k = 0; k < nfields; k++) {              // every struct field is its own cargo
    fv = field[k];
    if (fv == 0 || fv == 0xBADADD85) continue; // skip null + failed-read
    vh = ((pc ^ fv) + k*0x9E3779B9) * 0x9E3779B97F4A7C15;  // ← the fold
    vb = vh >> 48;                             // 16-bit bucket
    if (!seen(val_seen, vb)) {                 // FIRST time only
        mark(val_seen, vb);
        ctr[path_n + vb % val_n]++;         // reward: a novel (pc,value)!
    }
}

The + k * 0x9E3779B9 keeps the same value distinct depending on which field it came from, and the big multiply by the 64-bit golden-ratio constant avalanches the bits so near-neighbor pairs don't collide in the top 16 bits we actually use. The val_seen gate is what makes this bounded: a loop that reads the same length a million times mints exactly one lamp, not a million. Without it, the value neighborhood would flood and saturate just like the path one — and you'd be back to a bored lamplighter, only noisier.

05The trade-off

The second axis isn't free

A new signal always sends a bill. PC⊕VAL buys depth — but it costs map space, adds a noise risk, and blurs the tidy “are we done yet?” line that plain edge coverage gives you. An engineer should be able to argue both sides, so here it is, aspect by aspect:

AspectPC only — edgePC ⊕ VAL — dataflow
Same PC, new value Invisible — one lamp forever Distinguished — a fresh lamp
Escaping a plateau Stuck once every edge is seen Keeps finding while values vary
Boundary-value bugs (0, −1, huge len) No pull toward them Each novel value is rewarded
“Am I done?” signal Clean — saturates, easy to read Muddier — value axis keeps drifting up
Map pressure & collisions Compact — few features Many features; needs a big map + a bound
Noise resistance Immune — edges are finite Floods without the first-seen gate
Corpus size Small — few inputs kept Larger — more inputs judged “interesting”
Runtime overhead Cheap — one counter bump Extra reads, field decode, a hash

✓ a win  ·  ✗ a cost  ·  ± depends. The pattern is clean: PC-only wins on economy and clarity; PC⊕VAL wins on reach.

Which is why the design doesn't choose — it runs both at once. The path region gives you edge coverage's cheap breadth and its clean saturation signal; the value region adds depth only where inputs keep producing genuinely new values. On a fresh target edge coverage races to breadth fast; the moment it plateaus, the value axis is what keeps the fuzzer moving. And because the value axis can be switched off (KSMBDZZER_ENGINE=pc-*), you can always measure exactly what the second axis earned — a cost you can't justify is a cost you shouldn't pay.

06Integrating comparisons

Where should a comparison go?

The compiler can instrument every comparison too — __sanitizer_cov_trace_cmp* hands you, for each if (a == b), the site (PC) and both operands. That's gold for beating magic-byte and checksum checks. The question is how to spend it — and two philosophies lead to very different formulas:

Scheme A — operand as coverage
PC ⊕ CMP

Treat the comparison operand exactly like a dataflow value and fold it into the value map. This is what libFuzzer's value profile does: reaching a comparison with a never-seen operand mints a new feature.

✗ operand is input-echo → the map floods

Scheme B — context + directed solve
(PC + CMP) ⊕ VAL

Let the comparison only refine the location (which compare, resolved which way) in the PATH region, keep ⊕ VAL for genuine kernel arguments and returns, and hand the operand pair to the i2s mutator to solve the check outright.

✓ three concerns cleanly separated

The trap is that CMP means two different things here. In Scheme A it's the operand value — and operands are usually your own input bytes echoed straight back. If four input bytes flow into a in if (a == MAGIC), then every mutation makes a different, so PC ⊕ CMP is “new” on every single run. The map fills with input noise, the first-seen gate saturates almost instantly, and you still can't tell a guess creeping toward MAGIC from one wandering away. Worse, those noisy operand features share the value map with your real dataflow values and drown them out.

In Scheme B, CMP is only a small context tag — which comparison, and how it resolved — added onto the PC so the location becomes more specific (context-sensitive coverage). It's bounded: there are finitely many comparison sites, so it saturates cleanly like the rest of the path region. The genuine value fold ⊕ VAL stays reserved for arguments and returns. And the part that actually beats the check isn't coverage at all — the operand pair goes to mutate_i2s: “the kernel just compared your bytes at offset 12 against 0xFE534D42 → write 0xFE534D42 there.” One directed copy instead of 2³² blind guesses.

What the codebase actually does. kcov-dataflow follows Scheme B: cmp records are excluded from the ⊕ VAL value region (the rt != 0xC guard in fb()), reaching a comparison is still credited by the path bulk, and the operand pair drives mutate_i2s. Scheme A's value-profile is a fine tool for a pure-userspace target — but on a kernel where the same map must also carry real argument and return dataflow, letting input-echo operands share it is a net loss.
07Beyond the fold

The value axis pays off beyond coverage

Once the kernel is handing you real runtime values, the coverage map isn't the only place they help:

Return values become dictionary tokens. A value the kernel produced (a handle, an ID, a computed length in a ret record) is stashed and later spliced back into the fuzzer's input. If the kernel checks if (reply_id == request_id) later, the fuzzer already has the magic number to satisfy it. This “feed the output back into the input” idea is RedQueen's input-to-state correspondence, applied to return flow. (The comparison side of this — why cmp operands feed the mutator instead of the map — is Scheme B in the previous section.)

There's an off switch, on purpose. Setting KSMBDZZER_ENGINE=pc-* drops the value region entirely, leaving pure PC coverage — exactly what an edge fuzzer sees. That's not a bug, it's the control group: run the same target both ways and you can measure whether the (PC, value) vector actually finds more than PC alone. A claim about a new coverage signal is only worth something if you can turn it off and watch the results get worse.

08Where the idea comes from

Standing on a decade of coverage research

Folding values into the coverage signal isn't a bolt from the blue — it's the latest step in a long conversation about what a fuzzer should measure. The lineage worth knowing:

2013→
AFL & edge coverage. Established the branch/edge bitmap as the feedback signal that made coverage-guided fuzzing explode. Also the source of the saturation ceiling this whole design is fighting.
2016→
kcov & syzkaller (Linux). Brought edge coverage into the kernel; KCOV_TRACE_CMP later exposed comparison operands. kcov-dataflow is a sibling mechanism — a separate /sys/kernel/debug/kcov_dataflow device carrying values, not just PCs.
2017
VUzzer (Sanabria et al., NDSS). Data-flow / taint features to guide mutation — an early argument that what flows, not just where, should steer the fuzzer.
2016
laf-intel & libFuzzer value profile. Split multi-byte comparisons into single bytes, and fold comparison operands into a value table — the concrete instance of “Scheme A” (operand-as-coverage) discussed above.
2018
Angora (Chen & Chen, S&P). Byte-level taint plus gradient descent on comparison operands to solve hard branch conditions — the intellectual cousin of the i2s mutator here.
2019
RedQueen (Aschermann et al., NDSS). Input-to-state correspondence: values seen at runtime get written back into the input, cheaply solving magic-byte and checksum checks. Directly the ancestor of the return-value dictionary and mutate_i2s.
2020
Ijon (Aschermann et al., S&P). The closest kin: it lets you fold program state values into the coverage map to escape plateaus edge coverage can't. kcov-dataflow automates that folding for kernel arguments and returns instead of asking a human to annotate it.

Read together, the arc is simple: the community kept discovering that the runtime values a program computes are too useful to throw away. The PC ⊕ VAL fold is one compact way to keep them — a second axis on a wall of lamps that used to have only one.
