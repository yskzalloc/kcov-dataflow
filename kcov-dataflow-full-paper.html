State-aware KCOV: Compiler-Instrumented Data Flow Tracing for Kernel Memory Corruption Analysis

A Compiler-Kernel Co-designed System for Capturing Function Arguments and Return Values with Struct Field Expansion

Abstract. We present KCOV Dataflow, an extension to the Linux kernel's KCOV infrastructure that captures function arguments and return values—including inner struct field expansion—at runtime. By combining an LLVM IR instrumentation pass with a fault-tolerant kernel backend exposed via a dedicated /sys/kernel/debug/kcov_dataflow device, our system produces a chronological record of how data propagates through kernel subsystems. Unlike sanitizers that report only the crash site, our approach reveals the complete data flow context: what values entered a function, how they were transformed, and what was returned. We demonstrate the system on three memory corruption classes and a 10-deep nested call chain, showing that entry/exit traces precisely capture the moment of corruption and enable root cause identification without iterative debugging. The system maintains full backward compatibility with existing KCOV users and requires only a single Makefile line to enable for any kernel module.

1. Introduction

Kernel memory corruption bugs—use-after-free, out-of-bounds access, double-free—remain the dominant class of exploitable vulnerabilities in the Linux kernel. While sanitizers like KASAN detect that corruption occurred, they do not reveal how corrupted data propagated through the system. A KASAN report shows a single point-in-time snapshot. The analyst must then manually reconstruct the data flow.

This paper presents KCOV Dataflow, a compiler-kernel co-designed system that automatically captures:

  1. Function arguments on entry — including dereferencing pointer-to-struct arguments to record each field's value
  2. Return values on exit — capturing the post-mutation state of returned structs
  3. Argument metadata — index, byte size, and struct layout extracted from DWARF debug information

1.1 Contributions

  • An LLVM instrumentation pass (-fsanitize-coverage=dataflow-args,dataflow-ret) that extracts struct field offsets from DebugInfo
  • A kernel backend with fault-tolerant field dereferencing, atomic TLV buffer, and a dedicated debugfs device independent from legacy KCOV
  • A kernel build system integration (KCOV_DATAFLOW) enabling tracing without manual compiler flags
  • Empirical demonstration on OOB write, UAF write, double-free write, and a 10-deep nested call chain
  • Verification via drgn on both /proc/kcore (live) and vmcore (post-mortem)

2. Background

2.1 KCOV

KCOV [1] instruments kernel code to record which basic blocks execute during a syscall. Fuzzers like syzkaller [2] use this for coverage-guided mutation. KCOV captures control flow but not data flow.

2.2 KASAN

KASAN [3] detects memory safety violations via shadow memory. It reports the access type, address, and call stack—but not how the pointer became invalid or what struct fields were corrupted.

2.3 The Gap

Consider a use-after-free where function A frees an object, function B receives the dangling pointer, and function C writes through it. KASAN reports the write in C. But: what did B see when it received the pointer? Were fields already poisoned? Our system answers these questions automatically.

4. Implementation

4.1 LLVM Pass

The pass operates in ModuleSanitizerCoverage::instrumentFunction(). For each function with a DISubprogram:

  • Entry: For each argument, extract type from DISubroutineType. If pointer-to-struct, collect field offsets. Emit callback with (pc, arg_idx, arg_size, ptr, offsets, num_fields).
  • Exit: Use EscapeEnumerator to find all returns. Extract ReturnInst::getReturnValue(). Emit callback with (pc, ret_size, ptr, offsets, num_fields).

4.2 Opaque Pointer Handling

Modern LLVM uses opaque pointers (ptr). The pass bypasses this by exclusively using DWARF debug metadata (DIType hierarchy), which preserves full type information regardless of IR pointer representation.

4.3 Type Hash

An FNV-1a hash of the struct name is stored at offsets[-1] (one element before the pointer passed to the callback). This enables struct type identification without string comparison in the kernel.

4.4 Kernel Backend Safety

  • Recursion: notrace __no_sanitize_coverage noinline on all callbacks
  • Fault tolerance: copy_from_kernel_nofault() for every pointer dereference (offsets array, field values)
  • Atomicity: xadd() reserves buffer space atomically; undo on overflow
  • Per-task seq: task→kcov_dataflow_seq (survives CPU migration, unlike per-CPU counters)

5.4 Case 4: 10-Deep Nested Call Chain

An attacker-controlled payload_offset=16 propagates through 10 functions:

entry_handler(buf) → parse_request → validate_header(hdr{offset=16})
  → extract_payload(buf, offset=16) → transform_data(pl, 16) = 48
  → apply_filter(pl, 48) = 24 → compute_index(48, 24) = 8
  → lookup_slot(table, 8) → write_slot(table, 8)
  → commit_write(table, index=8) ← OOB! (slots[0..7] only)

The dataflow trace reveals: validate_header passes without checking offset bounds, and lookup_slot uses % 16 instead of % 8. Root cause identified from a single execution trace.

7. Compatibility

The system is designed for zero interference with existing KCOV users:

  • Separate device (/sys/kernel/debug/kcov_dataflow), separate ioctl namespace ('d' vs 'c')
  • Separate buffer (task→kcov_df_area vs task→kcov_area)
  • Callbacks check task→kcov_df_enabled — if no task enables it, zero overhead
  • Can run simultaneously with legacy KCOV (both devices open at once)

8. Mapping KCOV + KCOV Dataflow

Both record the same PC. The Nth occurrence of func+0x0 in the kcov PC buffer corresponds to the Nth ENTRY for that PC in kcov_dataflow. Ordering is guaranteed by single-task sequential execution. No shared counter needed.

For multiple calls to the same function: walk both buffers forward, matching by occurrence count. Nested calls are resolved by maintaining a call stack during post-processing.

9. Limitations and Future Work

  • Debug info required: Without -g, no struct expansion. The KCOV_DATAFLOW Makefile variable auto-adds it.
  • -O2 eliminates scalar args: At -O2, alloca+store for scalars may be optimized away. Struct pointer args are always reliable.
  • Single-level expansion: Nested struct pointers not recursively followed (future work).
  • Inlining: -fno-inline prevents loss of function boundaries but may alter behavior.
  • Future: Syzkaller integration, trace_event output, nested struct expansion, field name symbolization, temporal timestamps.

10. Conclusion

KCOV Dataflow bridges the gap between coverage-guided fuzzing (control flow) and memory safety detection (crash reports). By capturing the complete data state at function boundaries, it transforms crash analysis from iterative manual debugging into single-execution observation. The entry/exit traces directly answer: "What did this function receive? What did it return? How did the struct change?" For the 10-deep call chain case, the root cause (missing bounds check in validate_header) is immediately visible from the dataflow trace alone.

The system integrates cleanly into the kernel build infrastructure, requiring only KCOV_DATAFLOW_file.o := y to enable—making it accessible to kernel developers and fuzzer authors without compiler expertise.

5.8 Pointer Dereference and Dynamic Struct Capture

Q: Can kcov-dataflow capture struct fields from dynamically allocated (heap) memory?

A: Yes. The kernel callback performs one level of pointer dereference at runtime, reading struct fields from any valid kernel address—heap, stack, or static.

Mechanism

When a function parameter is a pointer to a struct (e.g., struct session_data *sd where sd was kmalloc'd):

  1. LLVM pass emits the pointer value and compile-time offset array
  2. At runtime, callback computes: field_addr = ptr + offset[i]
  3. Reads via copy_from_kernel_nofault(field_addr, size)
  4. Stores value in ring buffer

Proof: Actual Output

[ENTRY] seq=9 pc=rust_process_data arg[0](8) ptr=0x888007f6fdb0
  val = 0xcafe              ← data->id    (offset 0, heap-allocated)
  val = 0xdeadbeef12345678  ← data->value (offset 8, heap-allocated)
  val = 0xa                 ← data->flags (offset 16, heap-allocated)

What It Can and Cannot Read

ScenarioWorks?Behavior
Pointer to heap struct (kmalloc'd)YesReads actual field values
Pointer to stack structYesReads actual field values
Pointer to freed slab (KASAN poison)YesReads poison bytes (0xfd/0xff) — reveals object was freed
Pointer to unmapped pageSafecopy_from_kernel_nofault returns error, value stored as 0
ERR_PTR (-ENOMEM etc.)SkippedDetected via IS_ERR_VALUE, not dereferenced
NULL pointerSkippedDetected and skipped (no crash)
Double pointer (struct **pp)PartialReads *pp (the pointer value), not **pp
Nested struct (struct a { struct b inner; })YesDICompositeType includes nested fields with correct offsets
Pointer field inside struct (char *buf)PartialReads the pointer value, not the pointed-to data

Design Choice: Shallow Capture (One Level)

We perform exactly one level of dereference (pointer → struct fields). We do NOT chase pointers inside the struct. Reasons:

  • Performance: Bounded cost O(n) where n = number of struct fields
  • Safety: No recursive faults on invalid nested pointers
  • Sufficiency: The pointer value itself is informative (NULL = freed, 0xffff888... = valid heap, 0xfdfd... = KASAN poison)

6. Boundary Contract Runtime Verification

6.1 Functions as Black-Box Subsystems

Every kernel function call is a boundary between a caller (who provides inputs) and a callee (a black box from the caller's perspective):

Caller → [arg₁, arg₂, ..., argₙ] → f_callee (black box) → [ret] → Caller

The caller cannot observe what happens inside the callee. kcov-dataflow captures both sides of this boundary—making the black box transparent without modifying it.

6.2 Formal Boundary Contracts

Define a Boundary Contract C(f) = (P, Q) for function f:

  • P(args): precondition predicate over input arguments
  • Q(args, ret): postcondition predicate over return value given inputs

Example: For binder_alloc_buf(alloc, data_size, offsets_size, is_async):

P: data_size ≤ 2²⁰ ∧ offsets_size ≤ 2¹⁶
Q: ret == 0 → alloc.buffer ≠ NULL

A contract violation occurs when:

  • The caller passes arguments violating P (caller bug), or
  • The callee returns values violating Q given valid inputs (callee bug)

6.3 The Unknown Kernel Path Problem

When a user-space process calls write(binder_fd, data, len), it triggers a chain of kernel functions it cannot predict:

sys_write → vfs_write → binder_write → binder_thread_write →
  binder_transaction → binder_alloc_buf → ...

The user cannot pre-define which functions to monitor. Linux RV requires this pre-definition. kcov-dataflow captures every function boundary automatically—the offline verifier checks each captured (args, ret) pair against a contract database.

6.6 Key Insight

Linux RV verifies what we anticipated (pre-defined state machines on known events). kcov-dataflow verifies everything that actually happened (arbitrary value contracts on every function boundary the process touched). This transforms runtime verification from "verify anticipated behavior" to "verify all observed behavior."
